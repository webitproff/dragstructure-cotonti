## Коротко о плагине

**Drag & Drop Structure** — это административный плагин для Cotonti, который превращает рутинную работу со структурой сайта в простое и наглядное перетаскивание категорий мышкой.

Если вы когда-нибудь пытались перестроить каталог интернет-магазина, реорганизовать разделы блога или навести порядок в дереве статей через штатный раздел «Структура» Cotonti — вы знаете, насколько это утомительно: десятки текстовых полей, числовые пути, риск ошибиться и сломать иерархию. Плагин **полностью убирает эту боль**: вы видите перед собой живое дерево своих категорий и просто перетаскиваете их туда, куда нужно.

Один клик мышкой — и раздел «Игровые ноутбуки» переезжает из «Ноутбуков» в новый раздел «Игровое железо». Все вложенные подкатегории автоматически переезжают вместе с ним. Порядок в базе данных пересчитывается мгновенно, кеш сайта сбрасывается, меню и хлебные крошки на публичной части сразу показывают новый результат.

**Никакого кода. Никаких числовых путей. Только мышка.**

---

## Для кого этот плагин

Плагин создан для **администраторов сайтов на Cotonti**, которые:

- **ведут интернет-магазин** и хотят управлять структурой каталога товаров;
- **пишут блог или статьи** и хотят удобно группировать рубрики;
- **развивают форум** и хотят переставлять разделы без правки базы;
- **управляют портфолио** и хотят показывать работы в нужном порядке;
- **администрируют любой проект** с большим числом категорий и подкатегорий.

Плагин **не требует** знаний программирования. Если вы умеете перетаскивать иконки на рабочем столе — вы умеете пользоваться этим плагином.

## Ключевые возможности

### 🖱️ Перетаскивание категорий мышкой

Полноценный drag-and-drop интерфейс на базе библиотеки SortableJS. Категории перетаскиваются в любое место дерева: выше, ниже, внутрь другой категории, на верхний уровень. Всё интуитивно и наглядно.

### 🌳 Полное дерево категорий

В отличие от штатного раздела «Структура» Cotonti, где категории отображаются плоским списком с отступами, плагин показывает **настоящее дерево**: видно, кто кому родитель, кто ребёнок, кто внук. На каждом уровне — своя визуальная группировка.

### 🔄 Автоматический пересчёт путей

Внутренние числовые пути категорий (`structure_path`) пересчитываются автоматически при каждом перемещении. Плагин делает это по строгим правилам Cotonti: корневые категории нумеруются с шагом 10 (`010`, `020`, …), вложенные — с шагом 1 (`001`, `002`, …). Вам не нужно вникать в это — просто перетаскивайте.

### 📦 Перемещение целыми поддеревьями

Если у категории есть дочерние разделы, а у них — свои дочерние, все они **переезжают вместе с родителем**. Один раз перетащили — вся ветка в новом месте. Не нужно вручную перетаскивать каждого потомка.

### 🛠️ Восстановление структуры одной кнопкой

Служебная функция **«Нормализовать пути»** помогает, если структура по каким-то причинам сломалась (дубликаты путей, «слипшиеся» значения после ошибки импорта или сбоя предыдущей версии плагина). Одна кнопка — и все категории получают гарантированно уникальные чистые пути. Иерархию потом расставите заново перетаскиванием.

### ⚡ Мгновенное обновление сайта

После каждого перемещения плагин **сбрасывает кеш Cotonti**. Это значит, что изменения на публичной части (в меню, хлебных крошках, страницах категорий) видны сразу — без ожидания и без ручной очистки кеша.

### 🔒 Полная интеграция с правами Cotonti

Доступ к плагину контролируется штатной системой прав. По умолчанию страница доступна только администраторам сайта. Вы можете выдать доступ конкретным группам через раздел «Права».

### 📝 Логирование действий

Каждое перемещение записывается в системный лог Cotonti: кто, когда, в какой области менял структуру. Найти записи можно в разделе **«Лог»** админ-панели.

### 🌍 Мультиязычность

Плагин поставляется с русской и английской локализацией. Добавить свой язык — просто: скопируйте языковой файл и переведите значения.

### 🎯 Работа со всеми областями структуры

Плагин **универсален** — он работает не только с магазином или блогом, а со **всеми** расширениями Cotonti, которые поддерживают структуру: `page`, `market`, `forums`, `folio`, `usercategories` и любые другие. Один инструмент — единый интерфейс для всех разделов сайта.

## Что плагин НЕ делает — и почему это хорошо

Плагин **намеренно узкоспециализирован**. Он делает одну задачу — управление порядком и вложенностью категорий — и делает её хорошо. Всё остальное остаётся за штатными инструментами Cotonti:

- **Создание** новых категорий — через `admin.php?m=structure`.
- **Удаление** категорий — через `admin.php?m=structure`.
- **Редактирование** названий, описаний, иконок, шаблонов — через `admin.php?m=structure`.
- **Управление правами** доступа — через `admin.php?m=rights`.
- **Пересчёт счётчиков** элементов — через `admin.php?m=structure&a=resyncall`.

Такое разделение — это **сознательное архитектурное решение**. Плагин не дублирует функциональность ядра и не конфликтует с ним. Он аккуратно дополняет Cotonti там, где штатный интерфейс неудобен.

**Плюс для вас:** плагин можно безопасно отключить в любой момент — структура сайта и все данные останутся нетронутыми. Он не создаёт собственных таблиц в базе и не изменяет ядро.

## Как это выглядит

Страница плагина открывается в админ-панели по адресу `admin.php?m=other&p=dragstructure` и содержит:

- **выпадающий список** для выбора области структуры (`market`, `page`, `forums` и т.д.);
- **дерево категорий** с ручками для перетаскивания и визуальной иерархией;
- **кнопку «Нормализовать пути»** для восстановления сломанной структуры;
- **информационную панель** с сообщениями о результате операций.

## Установка

Установка занимает меньше минуты:

1. **Загрузите файлы** плагина в каталог `plugins/dragstructure/` вашего сайта.
2. Откройте **`admin.php?m=extensions`** — в списке появится новый плагин **Drag & Drop Structure**.
3. Нажмите **«Установить»** (активировать).
4. Откройте **«Инструменты»** в левом меню админки — увидите пункт **Drag & Drop Structure**.
5. Готово — можно перетаскивать категории.

Если пункт не появился — проверьте, что у вашей группы есть права на плагин (выдаются в `admin.php?m=rights`).

## Безопасность

Плагин следует всем стандартам безопасности Cotonti:

- **CSRF-защита** — каждый AJAX-запрос проверяется штатным X-токеном Cotonti.
- **Проверка прав** — страница и AJAX-обработчик защищены проверкой `cot_auth`.
- **XSS-защита** — все данные экранируются при передаче в шаблон.
- **SQL-инъекции** — все запросы используют prepared statements.
- **Транзакции** — перемещение выполняется атомарно: либо всё применилось, либо ничего.

## Часто задаваемые вопросы

**Вопрос:** Плагин работает на моей версии Cotonti?
**Ответ:** Плагин не тестировался на совместимость со всеми версиями Cotonti, которые ниже актуальной 1.0.0.

**Вопрос:** Сломаются ли URL-адреса страниц после перетаскивания?
**Ответ:** Нет. Плагин меняет только порядок и вложенность, но **не трогает коды категорий** (`code`), от которых зависят адреса. Все ссылки продолжат работать.

**Вопрос:** Что будет, если я отключу плагин?
**Ответ:** Ничего страшного. Плагин не имеет собственных таблиц в базе и не изменяет ядро. Структура сайта останется в том виде, в котором вы её оставили. Отключение затрагивает только интерфейс.

**Вопрос:** Плагин работает с несколькими языками сайта?
**Ответ:** Да. Плагин поставляется с русской и английской локализацией. При необходимости можно добавить другие языки, скопировав и переведя языковой файл.

**Вопрос:** Что делать, если структура сломалась?
**Ответ:** Используйте кнопку **«Нормализовать пути»** — она перестроит все пути в чистый плоский вид. После этого иерархию можно расставить заново перетаскиванием. Подробнее — в разделе «Порядок сортировки категорий при помощи плагина» ниже.

**Вопрос:** Можно ли перетаскивать категории, содержащие товары?
**Ответ:** Да. Перетаскивание родительской категории автоматически переносит всё её поддерево. Сами товары при этом **не покидают свою категорию** — они остаются привязанными к своему разделу и просто переезжают вместе с ним.

**Вопрос:** Нужны ли специальные знания или навыки программиста?
**Ответ:** Нет. Плагин полностью готов к использованию и не требует ни правки файлов, ни настройки кода. Всё делается мышкой в админке.

# Порядок сортировки категорий при помощи плагина

## Простое руководство для администратора интернет-магазина

> **Для кого этот раздел:** для администратора сайта, который управляет каталогом товаров или блогом через Cotonti. Не для программиста. Здесь нет кода — только то, что вы видите на экране, и что нужно сделать мышкой.

---

## Что такое «порядок категорий» и зачем он нужен

Любой интернет-магазин или блог состоит из **категорий** — разделов, по которым разложены товары или статьи. Например, в магазине электроники есть разделы «Компьютеры», «Ноутбуки», «Смартфоны», а внутри них — подразделы вроде «Игровые ноутбуки», «Ультрабуки», «Рабочие станции».

У каждой категории в Cotonti есть два важных свойства:

1. **Где она находится** — в каком родительском разделе (или в самом верху, на главном уровне).
2. **В каком порядке она стоит** — какая категория показывается первой, какая второй, какая последней.

И то, и другое можно менять вручную через штатный раздел «Структура» в админке — но там это делается через неудобные числа и текстовые поля. Плагин **Drag & Drop Structure** превращает эту работу в простое перетаскивание мышкой: вы берёте категорию и ставите её туда, куда нужно — как перетаскиваете иконки на рабочем столе.

**Зачем вообще менять порядок и вложенность:**

- Чтобы **важные разделы были наверху** — например, «Акции» или «Новинки» первыми в меню.
- Чтобы **логично сгруппировать товары** — например, «Игровые ноутбуки» поместить внутрь «Ноутбуков», а не держать их в общем списке.
- Чтобы **навести порядок после импорта** — если категории загрузились вперемешку.
- Чтобы **поменять структуру каталога** под сезон или новую линейку товаров.

## Как открыть страницу плагина

1. Зайдите в админку сайта — `ваш-сайт.ru/admin.php`.
2. В левом меню выберите раздел **«Инструменты»** (или «Other»).
3. Найдите пункт **«Drag & Drop структура»** — это и есть наш плагин.
4. Откроется страница с деревом категорий.

Если вы не видите пункт в меню — значит, у вашей учётной записи нет прав на плагин. Обратитесь к суперадминистратору сайта, чтобы он выдал права.

---

## Что вы видите на странице

В верхней части страницы — **выпадающий список «Расширение»**. В нём перечислены все области структуры сайта: `page` (страницы и статьи), `market` (интернет-магазин), `forums` (форумы), `folio` (портфолио) и т.д.

- Для интернет-магазина выберите **`market`**.
- Для блога или статей — **`page`**.

После выбора в списке страница **перерисуется** и покажет дерево категорий именно этой области.

**Что такое дерево категорий:**

Каждая категория выглядит как прямоугольная плашка примерно такого вида:

```
⋮⋮  001.001.001  gaming-desktops — Gaming Desktops
                  High-performance gaming PCs.
```

Что здесь что:

| Элемент | Что это |
|---|---|
| `⋮⋮` (слева) | **Ручка** — за неё нужно тянуть мышкой |
| `001.001.001` | Технический номер (путь) — для администратора это просто ориентир, не трогайте его |
| `gaming-desktops` | Код категории (латиницей) — используется в адресах страниц |
| **Gaming Desktops** | Название категории — то, что видят посетители |
| Мелкий серый текст снизу | Описание категории |

Категории вложенные показываются **с отступом вправо** и с вертикальной линией слева — так видно, кто в кого вложен.

В самом низу каждой категории есть **пустая серая зона** — туда можно перетащить другую категорию, и она станет дочерней.

---

## Основная операция: как перетащить категорию

Всё делается **мышкой** — никаких кнопок «вверх/вниз» нажимать не нужно.

1. **Возьмите категорию за ручку.** Наведите курсор на иконку `⋮⋮` слева от названия. Курсор превратится в «лапку». Зажмите левую кнопку мыши **и не отпускайте**.
2. **Потяните.** Категория «оторвётся» от места и последует за курсором. Она будет показана полупрозрачной — так вы видите, что тащите именно её.
3. **Наведите на нужное место.** Появится **серая полоса-подсказка** — это место, куда категория встанет, если вы отпустите кнопку сейчас.
4. **Отпустите кнопку мыши.**

Через 1–3 секунды вы увидите, что дерево перерисовалось в новом порядке. Это значит, что изменения уже сохранены на сервере.

> **Важно:** если что-то пошло не так (например, сервер вернул ошибку), вы увидите всплывающее окно с текстом ошибки, а страница перезагрузится. Не пугайтесь — это защита. Просто попробуйте ещё раз.

## Пример на реальных категориях магазина

Давайте разберём это на конкретном каталоге интернет-магазина электроники. У нас есть пять корневых разделов:

```
001  Computers & Components
002  Laptops
003  Smartphones
004  Game Consoles
005  Accessories
```

И у каждого — свои подразделы. Например, у `Laptops`:


### Сценарий 1. Поменять местами два подраздела

**Задача:** хотим, чтобы в блоке «Ноутбуки» **«Ультрабуки»** шли **до** «Игровых ноутбуков» (потому что ультрабуки покупают чаще).

**Было:**

```
Laptops
├── Gaming Laptops
├── Ultrabooks
└── Workstations
```

**Что делаем:**

1. Находим в дереве `Ultrabooks`.
2. Берём за ручку `⋮⋮` и тащим вверх, пока серая полоса не окажется **над** «Gaming Laptops».
3. Отпускаем.

**Стало:**

```
Laptops
├── Ultrabooks
├── Gaming Laptops
└── Workstations
```

Порядок поменялся. При этом **все три категории остались внутри «Laptops»** — вложенность не изменилась. Изменился только порядок вывода.

**Что важно знать:**

- Коды категорий (`ultrabooks`, `gaming-laptops`) **не изменились**.
- Ссылки на страницы **не сломались** — все закладки и ссылки из поиска работают.
- В публичной части сайта меню и хлебные крошки сразу покажут новый порядок.

### Сценарий 2. Переместить подраздел в другого родителя

**Задача:** раздел «Игровые ноутбуки» нужно перенести из «Ноутбуков» в новый раздел **«Игровое железо»** (который вы только что создали в штатном разделе «Структура»).

```
    ├── High-End Gaming
    ├── Mid-Range Gaming
    └── Budget Gaming
```

**Что делаем:**

1. Находим `Gaming Laptops` в дереве.
2. Берём за ручку `⋮⋮`.
3. Тащим вниз, к новой категории `Gaming Hardware` — **не в неё саму, а внутрь**. Когда наведётесь на серую пустую зону под названием `Gaming Hardware`, появится подсказка «сюда».

**Стало:**

```
Gaming Hardware
└── Gaming Laptops
    ├── High-End Gaming
    ├── Mid-Range Gaming
    └── Budget Gaming
```

### Сценарий 5. Сгруппировать всё игровое в один раздел

**Задача:** разделы, связанные с играми, сейчас разбросаны: «Game Consoles», «Gaming Laptops» (внутри ноутбуков), «Gaming Keyboards» (внутри аксессуаров). Хотим собрать всё в один корневой раздел **«Gaming»**.

## Что происходит после перетаскивания

Вы отпустили мышку. Что происходит «под капотом»:

1. **Плагин сохраняет новый порядок в базе данных.** Мгновенно, автоматически, без вашего участия.
2. **Дерево на странице перерисовывается.** Если что-то пошло не так — вы увидите ошибку.
3. **Меню и хлебные крошки на публичной части обновляются.** Следующий посетитель увидит уже новый порядок.
4. **Кеш сайта сбрасывается.** Именно поэтому изменения видны сразу, без ожидания.
5. **В журнал админки добавляется запись.** В разделе «Лог» (`admin.php?m=logger`) можно увидеть: кто, когда и в какой области менял структуру.

**Что НЕ меняется:**

- **Названия** категорий — остаются прежними.
- **Описания и иконки** — остаются прежними.
- **Коды категорий** (`code`) — остаются прежними, поэтому **все URL-адреса страниц сохраняются**. Если у вас была ссылка `site.ru/market/gaming-desktops`, она продолжит работать.
- **Права доступа** — остаются прежними.
- **Товары** — остаются в своих категориях, никуда не переносятся.

Меняется **только одно** — порядок и вложенность в дереве. Всё остальное плагин не трогает.

## Кнопка «Нормализовать пути» — что это и когда ей пользоваться

В верхней части страницы плагина есть красная кнопка **«Нормализовать пути»**. Она делает **очень серьёзную вещь**: **стирает всю вложенность** и превращает дерево в плоский список.

**Что это значит по-простому:** все категории становятся **корневыми**. Никаких подразделов не остаётся. Внутреннее содержимое (товары, статьи) не удаляется, но структура становится плоской:

**Было:**

```
Computers & Components
├── Desktop Computers
│   ├── Gaming Desktops
│   └── Office Desktops
└── Peripherals
    ├── Keyboards
    └── Mice
```

**После «Нормализации»:**

```
Computers & Components
Desktop Computers
Gaming Desktops
Office Desktops
Peripherals
Keyboards
Mice
```

Всё на одном уровне, порядок — по номерам, по возрастанию.

### Когда это нужно

**Только в одном случае:** когда структура «сломалась». Признаки поломки:

- В дереве появились **дубликаты путей** — например, две категории с одинаковым номером `001`. Плагин в такой ситуации не может корректно работать.
- Категории **пропали из дерева** или отображаются не на своих местах.
- Вы видите **ошибку** при попытке перетаскивания, и она не уходит.
- Структура была **импортирована из другой CMS** и содержит мусорные значения путей.

### Когда этого делать НЕ нужно

- **Просто так** — «на всякий случай». Это сотрёт вашу вложенность, которую вы, возможно, выстраивали месяцами.
- **Перед важным запуском** — не надо.
- **Если вам кажется, что «стало как-то не так»** — сначала убедитесь, что проблема действительно в структуре, а не в чём-то другом.

### Что делать, если всё-таки нажали

Плагин спросит подтверждение — **внимательно прочитайте текст** в диалоговом окне. Там написано, что иерархия будет потеряна. Если вы не уверены — нажмите **«Отмена»**.

Если подтвердили — в течение 2–3 секунд все категории станут корневыми. Дальше:

1. **Не паникуйте.** Данные не удалены.
2. **Восстанавливайте вложенность вручную** — перетаскиванием. Начните с крупных разделов, потом подразделов, потом внуков.
3. **Проверьте публичную часть** — меню и крошки сразу покажут новое состояние.

**Совет:** перед нажатием «Нормализовать» сделайте **скриншот дерева**. Это займёт 10 секунд, но если что-то пойдёт не так — у вас будет шпаргалка, как было.

## Частые ошибки и как их избежать

### Ошибка 1. «Я перетащил, но ничего не произошло»

**Причина:** скорее всего, вы **не зацепились за ручку** `⋮⋮`, а попытались тянуть за название. Или за ручку, но не зажали кнопку мыши.

**Решение:** берите строго за `⋮⋮` слева от названия, зажмите и держите, пока тянете.

### Ошибка 2. «Я перетащил, а категория пропала»

**Причина:** вы перетащили её **внутрь другой категории**, и она теперь не на верхнем уровне, а внутри. Разверните нужный родитель — категория там.

**Решение:** если хотите вернуть наверх — снова возьмите за ручку и тащите в корневую зону (ниже всех корневых, между ними).

### Ошибка 3. «При перетаскивании выскочила ошибка и страница перезагрузилась»

**Причина:** чаще всего это означает, что **пока вы тащили**, кто-то другой (или вы во второй вкладке) изменил структуру, и данные на странице устарели.

**Решение:** страница перезагрузилась — она уже показывает актуальные данные. Просто повторите действие.

Если ошибка повторяется — прочитайте текст. Часто там написано «Cannot move category into its own descendant» — это значит, что вы пытаетесь вложить родителя в собственного ребёнка. Так нельзя — это создало бы бесконечный цикл. Перетащите в **другое** место.

### Ошибка 4. «Категория не хочет перемещаться, её будто что-то держит»

**Причина:** возможно, вы пытаетесь положить категорию **в саму себя** или **в её собственный дочерний раздел**. Плагин это блокирует.

**Решение:** проверьте, куда именно вы тащите. Если родитель — сама категория или её ребёнок, выберите другое место.

### Ошибка 5. «После перетаскивания меню в публичной части не обновилось»

**Причина:** скорее всего, кеш на стороне браузера или внешнего прокси (Cloudflare, Varnish, nginx).

**Решение:** обновите страницу с принудительной перезагрузкой — `Ctrl + F5` (Windows/Linux) или `Cmd + Shift + R` (Mac).

Если не помогло — обратитесь к администратору сервера, возможно, нужно сбросить серверный кеш.

### Ошибка 6. «Я случайно нажал "Нормализовать", и всё сломалось»

**Причина:** вы нажали кнопку и подтвердили, что готовы потерять иерархию.

**Решение:** восстанавливайте вручную. Плагин не ведёт историю и не умеет отменять. Если у вас есть **резервная копия базы данных** — восстановите только таблицу `structure` через phpMyAdmin. Это самый быстрый способ.

**Совет:** уберите кнопку «Нормализовать» из шаблона, если она не нужна — передайте эту задачу администратору, который точно знает, что делает. Технически это одна строка в файле шаблона.

## Правила безопасной работы с плагином

Прочитайте эти правила — они сэкономят вам часы.

**Правило 1. Делайте изменения по одному.**

Не перетаскивайте пять категорий подряд за 10 секунд. Перетащили одну — посмотрите, что получилось, дождитесь перерисовки дерева. Потом следующую.

**Правило 2. Не работайте с плагином, если кто-то ещё правит структуру.**

Если у вас несколько администраторов — договоритесь, кто работает в какое время. Параллельные перемещения могут дать ошибку.

**Правило 3. Не переименовывайте категории в плагине — это не его работа.**

Плагин **не** меняет названия, описания, иконки. Для этого есть штатный раздел «Структура». Не пытайтесь найти в плагине поле «название» — его нет.

**Правило 4. Не удаляйте категории в плагине — это не его работа.**

Плагин **не** удаляет категории. Для удаления — штатный раздел «Структура».

**Правило 5. Не трогайте категорию `system`.**

Если у вас в дереве есть раздел с кодом `system` — это служебный раздел Cotonti (там хранятся системные страницы). Перетаскивать его **можно**, но **не нужно**: это может сломать служебные ссылки. Оставьте его в покое.

**Правило 6. Перед крупной реорганизацией — сделайте бэкап.**

Перед тем как перестраивать иерархию каталога из 200+ категорий, попросите хостера или администратора сделать резервную копию базы. Это займёт минуту и спасёт вас, если что-то пойдёт не так.

**Правило 7. Не трогайте кнопку «Нормализовать» без необходимости.**

Пользуйтесь только если структура сломана. См. раздел выше.

**Правило 8. После крупных изменений — проверьте публичную часть.**

Пройдите по сайту как посетитель: главное меню, хлебные крошки, страницы категорий. Убедитесь, что всё выглядит так, как вы планировали.

## Что делать, если что-то пошло совсем не так

**Ситуация 1. Дерево не отображается.**

Проверьте: выбран ли `ext` в списке. Если список пуст — значит, ни одно расширение не объявило структуру. Обратитесь к администратору: возможно, нужно активировать модуль `market` или `page`.

**Ситуация 2. Категория висит «в воздухе» — не в родителе, но и не в корне.**

Это признак повреждённой структуры. Попробуйте:

1. Открыть штатный раздел «Структура» и найти эту категорию.
2. Посмотреть её `path` — должен быть вида `001.002`, а не `001..002` или с другими ошибками.
3. Если путь битый — нажать «Нормализовать» (да, это единственный случай, когда стоит рискнуть).
4. После нормализации расставить иерархию заново.

**Ситуация 3. Ничего не помогает.**

- скриншот страницы плагина;

## 1. Введение

### 1.1. Назначение документа

Настоящее руководство представляет собой исчерпывающее техническое описание плагина **DragStructure** для Cotonti Siena CMF — расширения, которое добавляет в административную панель Cotonti визуальный редактор иерархии категорий с поддержкой drag-and-drop и автоматическим пересчётом числовых путей `structure_path`.

Документ предназначен для:
- администраторов сайтов на Cotonti, эксплуатирующих плагин;
- разработчиков расширений Cotonti, интегрирующих свои модули со структурой;
- системных интеграторов, выполняющих миграции и восстановление данных;
- технических писателей и сопровождающих документацию проекта.

### 1.2. Краткое описание плагина

**DragStructure** (код `dragstructure`) — административный плагин, решающий одну узкую, но критически важную задачу: **удобное управление порядком и иерархией категорий структуры Cotonti** без необходимости вручную редактировать числовые пути `structure_path` в форме штатного раздела «Структура».

Ключевые возможности:

- Древовидное отображение всех категорий выбранной области (`structure_area`) в административной панели.
- Перетаскивание категорий мышью (SortableJS) на любой уровень вложенности с автоматическим пересчётом путей.
- Автоматическая перенумерация `structure_path` в числовом формате:
  - корневые категории — трёхзначные с шагом 10 (`010`, `020`, `030`, …);
  - вложенные категории — трёхзначные с шагом 1 (`001`, `002`, `003`, …).
- Служебное действие «Нормализовать пути» — восстановление из разрушенного состояния БД.
- Мгновенная очистка кеша Cotonti и запись в системный лог.
- Полная CSRF- и XSS-защита, интеграция со штатной системой прав Cotonti.

### 1.3. Область применения

Плагин полезен в следующих ситуациях:

| Сценарий | Ценность плагина |
|---|---|
| Крупный каталог (100+ категорий) | Массовые перемещения и реорганизация без риска «сломать» пути |
| Миграция с другой CMS | Быстрое воссоздание иерархии после импорта |
| Ошибки предыдущих версий плагина/скриптов | Кнопка «Нормализовать» восстанавливает работоспособность |
| Тестирование структуры | Перебор вариантов иерархии в пару кликов |
| Мульти-областной сайт (`page`, `market`, `forums`, `folio`, `usercategories`) | Единый интерфейс для всех областей |

### 1.4. Что плагин **не** делает

- Не создаёт и не удаляет категории (это штатные операции Cotonti).
- Не управляет правами доступа (`cot_auth`) — они остаются за разделом «Права» ядра.
- Не редактирует заголовки, описания, иконки и шаблоны категорий.
- Не влияет на `structure_count` (счётчики элементов) — за это отвечают модули-владельцы области через `*_sync()`.
- Не работает в публичной части сайта — только в админ-панели.

## 2. Место плагина в архитектуре Cotonti CMF

### 2.1. Общий контекст Cotonti

Cotonti — модульный PHP-фреймворк (CMF), в котором всё построено на трёх базовых концепциях:

1. **Расширения** (модули `module` и плагины `plug`) — единицы функциональности, подключаемые через систему хуков.
2. **Структура** — универсальная иерархия категорий, единая для всех расширений (таблица `*_structure`).
3. **События/хуки** — механизм внедрения кода расширений в контрольные точки ядра.

Плагин `dragstructure` в этой схеме занимает **пограничное положение**:

- он является **плагином** (`plug`) — регистрируется в таблице `*_plugins`, активируется через админку;
- он работает **со структурой** — то есть с той же таблицей, что и модули `page`, `market`, `forums`, `folio`, `usercategories`;
- он **не объявляет собственной структуры** — в списке `cot_getExtensionsWithStructure()` его нет, что принципиально: плагин не является «областью» структуры, он лишь инструмент управления чужими областями;
- он подключается через **два хука**:
  - `tools` — точка входа в админ-панель;
  - `ajax` — точка приёма AJAX-запросов через `plug.php?r=dragstructure`.

### 2.4. Почему это именно плагин, а не модуль

Модуль Cotonti (`module`) обычно является самодостаточным расширением с собственной структурой и публичной частью. Плагин (`plug`) — расширение, внедряющееся в чужие точки через хуки.

`dragstructure` полностью соответствует определению плагина:

- **не имеет собственной структуры** в `*_structure`;
- **не имеет публичной части** (работает только в админке);
- **подключается через хуки** `tools` и `ajax`;
- **не имеет собственных таблиц** в БД;
- **не изменяет состав Cotonti** — просто удобный UI для существующих данных.

Это принципиально правильное архитектурное решение: плагин остаётся «инструментом», который можно безопасно отключить, не разрушая данные.

### 3.1. Системные требования

| SortableJS | Подключается из CDN или админ-темы | Локальная версия 1.15.2+ |

### 3.2. Установка

**Способ 1. Через админ-панель**

1. Зайти в `admin.php?m=extensions`.
2. Убедиться, что каталог `plugins/dragstructure/` загружен в корень сайта.
3. Найти плагин в списке «Плагины» — он появится автоматически после обновления списка.
4. Нажать «Установить» (активировать).

**Способ 2. Вручную**

1. Разместить файлы плагина в `plugins/dragstructure/`.
2. В админке зайти в «Расширения» → «Плагины».
3. Активировать `dragstructure`.

После активации:

- плагин появится в разделе **«Инструменты»** (`admin.php?m=other`);
- его настройки прав (Auth_guests/Auth_members) будут зарегистрированы в системе Cotonti.

### 3.3. Настройка прав

Файл `dragstructure.setup.php` содержит блок `[BEGIN_COT_EXT]` с параметрами:

```
Auth_guests=R
Lock_guests=12345A
Auth_members=RW
Lock_members=12345A
```

Что это значит:

- **Auth_guests=R** — гостям доступно «чтение» прав плагина (технически гость не имеет доступа к админке, но флаг фиксируется);
- **Auth_members=RW** — зарегистрированные пользователи получают R и W по умолчанию;
- **Lock_*** — заблокированные маски прав для гостей и пользователей.

**Практически**, доступ к странице `admin.php?m=other&p=dragstructure` проверяется **двумя** условиями (в `dragstructure.tools.php`):

```php
cot_block(cot_auth('admin', 'a') || cot_auth('plug', 'dragstructure', 'A'));
```

То есть администратор сайта (`admin.a`) или пользователь с правом `A` (admin) на плагин получает доступ. Группы прав назначаются в разделе **«Права»** Cotonti (`admin.php?m=rights`).

**Рекомендуемая настройка для боевого сайта:**

- право `A` на `dragstructure` — только для группы «Администраторы» (обычно COT_GROUP_SUPERADMINS = 5);
- право `R`/`W` — не выдавать никому, кроме администраторов, потому что плагин меняет структуру.

### 3.4. Проверка работоспособности

1. Открыть `admin.php?m=other&p=dragstructure`.
2. Убедиться, что в выпадающем списке «Расширение» присутствуют области (`page`, `market`, `forums`, `folio`, `usercategories` и т.п.).
3. Убедиться, что дерево категорий отрисовалось.
4. Перетащить одну категорию, проверить в БД изменение `structure_path` и запись в логе (`admin.php?m=logger`).

## 5. Ключевые концепции: structure_path, area, code, title

Прежде чем разбирать логику плагина, необходимо досконально понять модель данных Cotonti. Плагин манипулирует преимущественно полем `structure_path`, поэтому без понимания этой концепции дальнейший разбор бессмысленен.

### 5.1. Таблица `*_structure`

Таблица с префиксом, например `x92374_structure`:

```sql
CREATE TABLE `x92374_structure` (
  `structure_id`        mediumint UNSIGNED NOT NULL AUTO_INCREMENT,
  `structure_area`      varchar(64)  NOT NULL,       -- 'page', 'market', 'forums', ...
  `structure_code`      varchar(255) NOT NULL,       -- 'news', 'articles', 'php'
  `structure_path`      varchar(255) NOT NULL,       -- '001', '001.002', '980.010'
  `structure_tpl`       varchar(128) DEFAULT '',     -- имя шаблона или 'same_as_parent'
  `structure_title`     varchar(255) NOT NULL,       -- 'Новости', 'Статьи'
  `structure_desc`      text,                        -- произвольное описание
  `structure_icon`      varchar(128) DEFAULT '',     -- путь к иконке
  `structure_locked`    tinyint UNSIGNED DEFAULT 0,  -- 0/1 — заблокирована ли
  `structure_count`     mediumint UNSIGNED DEFAULT 0 -- счётчик элементов
);
```

**Ключевые поля для плагина:**

- `structure_id` — первичный ключ, используется как идентификатор узла в JS (`data-id`).
- `structure_area` — область, к которой относится категория.
- `structure_code` — символьный код категории (например, `news`); формирует URL (`index.php?e=page&c=news`).
- `structure_path` — **главное поле**, определяющее иерархию и порядок.
- `structure_title` — отображаемое название.

Поля `structure_tpl`, `structure_desc`, `structure_icon`, `structure_locked`, `structure_count` плагином **не изменяются** — он трогает только `structure_path` и, косвенно, служебное поле для транзакций.

### 5.2. Что такое `structure_path`

`structure_path` — это **числовая последовательность, разделённая точками**. Каждый сегмент — трёхзначное число (с ведущими нулями). Пример:

| id | code | path | title | Уровень |
|---|---|---|---|---|
| 1 | `root1` | `010` | Корень 1 | 0 |
| 2 | `root2` | `020` | Корень 2 | 0 |
| 3 | `child1` | `010.001` | Ребёнок 1 | 1 |
| 4 | `child2` | `010.002` | Ребёнок 2 | 1 |
| 5 | `grandchild` | `010.001.001` | Внук | 2 |
| 6 | `root3` | `030` | Корень 3 | 0 |

**Правила интерпретации:**

1. **Длина пути** (число точек + 1) — уровень вложенности:
   - `010` — уровень 0 (корень);
   - `010.001` — уровень 1;
   - `010.001.001` — уровень 2.

2. **Родитель** — это путь без последнего сегмента:
   - для `010.001` родитель — `010`;
   - для `010.001.001` родитель — `010.001`;
   - для `010` родителя нет (корневая).

3. **Порядок сортировки** — лексикографический по `structure_path`:
   - `010` < `020` < `030`;
   - `010.001` < `010.002` < `010.003`;
   - `010.001.001` < `010.001.002`.

4. **Сортировка в БД** — `ORDER BY structure_path ASC, structure_code ASC`. Именно это используется в `cot_load_structure()` и во всех выборках Cotonti.

### 5.3. Область структуры (`structure_area`)

`structure_area` — код расширения, к которому относится категория. Cotonti поддерживает **несколько независимых областей** в одной таблице:

- `page` — категории модуля Pages;
- `market` — категории модуля Market (маркетплейс);
- `forums` — категории (разделы) модуля Forums;
- `folio` — категории модуля Folio;
- `usercategories` — категории пользователей (плагин Usercategories);
- плюс любые другие расширения, объявившие хук `structure.extensions`.

Каждая область имеет **собственное пространство путей** — `structure_path` внутри одной области уникален, но между областями может совпадать.

### 5.4. Понятия «code» и «title»

- **code** — машинный идентификатор, стабильный, используется в URL. Обычно латиница, цифры, дефис.
- **title** — человекочитаемое название, может содержать любые символы.

`code` **не меняется** при перетаскивании — плагин работает только с `path`. Это критично: все ссылки в публичной части сайта (`index.php?e=page&c=news`) остаются валидными.

### 5.5. Логическая модель Cotonti

Загрузка структуры (`cot_load_structure()` в `system/functions.php`) строит ассоциативный массив:

```php
Cot::$structure[$area][$code] = [
    'path'   => '010.001',           // сквозной путь
    'tpath'  => 'Корень 1 / Ребёнок 1', // title-путь
    'rpath'  => '010.001',           // raw path (совпадает с path)
    'id'     => 3,
    'tpl'    => 'page',
    'title'  => 'Ребёнок 1',
    'desc'   => '',
    'icon'   => '',
    'locked' => 0,
    'count'  => 0,
];
```

Плагин **не модифицирует** этот массив — его пересчитывает `cot_load_structure()` при каждом запросе.

## 6. Порядок сортировки категорий при помощи плагина

Этот раздел — центральный в документации, так как именно порядок и иерархия — предметная область плагина.

### 6.1. Три уровня «порядка» в Cotonti

Понимание требует различать три концепции:

1. **Порядок в БД** (`ORDER BY structure_path`).
2. **Порядок в кеше** (`Cot::$structure`, отсортированный при загрузке).
3. **Порядок в UI** (DOM-дерево в админке, построенное по `CATS_JSON`).

Плагин обеспечивает **согласованность всех трёх**: после перемещения в БД все три уровня пересчитываются из одного источника — `structure_path`.

### 6.2. Правило числового формата

Формат `structure_path` в плагине:

- **корневой уровень**: сегмент = `sprintf('%03d', position * 10)` — то есть **`010`, `020`, `030`, …, `100`, `110`, …** с шагом **10** и шириной **3**.
- **вложенный уровень**: сегмент = `sprintf('%03d', position)` — то есть **`001`, `002`, `003`, …, `999`** с шагом **1** и шириной **3**.
- **полный путь**: `parentPath . '.' . segment`.

**Почему шаг 10 для корней и шаг 1 для детей?**

- **Корни** сортируются с запасом: при необходимости добавить новый корень между `020` и `030` можно вставить `025`, не пересчитывая соседей.
- **Дети** — плотная нумерация, потому что добавление детей — частая операция, и Cotonti ожидает плотных путей для сортировки без «дырок».

**Пример:**

| id | code | path | Уровень |
|---|---|---|---|
| 1 | `a` | `010` | 0 |
| 2 | `b` | `020` | 0 |
| 3 | `c` | `030` | 0 |
| 4 | `a1` | `010.001` | 1 |
| 5 | `a2` | `010.002` | 1 |
| 6 | `a1x` | `010.001.001` | 2 |
| 7 | `b1` | `020.001` | 1 |

### 6.3. Сценарии сортировки

#### 6.3.1. Перестановка соседей в одном контейнере

**Действие**: перетащить `a1` (path `010.001`) ниже `a2` (path `010.002`) в контейнере `010`.

**Отправка**: `parent_id=1` (id родителя), `order=[5, 4]` (сначала `a2`, потом `a1`).

**Результат**:

| id | path до | path после |
|---|---|---|
| 4 (`a1`) | `010.001` | `010.002` |
| 5 (`a2`) | `010.002` | `010.001` |

**Внутренние механизмы** (см. `dragstructure_apply_order`):

1. `movingIds = {4, 5}`.
2. `usedPaths = все пути, кроме 4 и 5`.
3. Для `order=[5, 4]` в контейнере `010`:
   - `pos=1` → `candidate = "010.001"` (свободен, так как `010.001` был путём `a1`, который перемещается);
   - `pos=2` → `candidate = "010.002"`.
4. **Фаза 1 (временные пути)**: обеим категориям присваивается `_t_<random>_<id>`, чтобы избежать конфликта UNIQUE, если на `structure_path` стоит уникальный индекс (в текущей схеме Cotonti его нет, но плагин защищается на будущее).
5. **Фаза 2 (финальные пути)**: `a2` → `010.001`, `a1` → `010.002`.

#### 6.3.2. Перемещение в другого родителя (без смены уровня)

**Действие**: перетащить `b1` (path `020.001`, родитель `020`) внутрь `010` (id 1).

**Отправка**: `parent_id=1`, `order=[…, 7]` (в новом порядке детей `010`).

**Результат**: у категории `b1` меняется префикс пути с `020.001` на `010.<segment>`. Сегмент выбирается `pos`-ом в `order`-е внутри `010`.

**Важно**: `b1` при этом сохраняет своих детей (если бы они были) — плагин **рекурсивно** пересчитывает потомков (`walkChildren`), потому что их пути начинаются с `020.001.` и становятся невалидными.

#### 6.3.3. Перемещение на уровень выше (в корень)

**Действие**: перетащить `a1` (path `010.001`) в корневой контейнер (`parent_id=0`).

**Отправка**: `parent_id=0`, `order=[1, 2, 3, 4]` (новый порядок корней).

**Результат**: `a1` получает путь вида `040` (следующий свободный с шагом 10). Прежние `010.001` — освобождается для других нужд.

#### 6.3.4. Перемещение с потомками

**Действие**: перетащить `a` (path `010`, есть дети `010.001`, `010.001.001`) в корень `b` (path `020`, если `b` станет новым родителем).

**Отправка**: `parent_id=2` (id `b`), `order=[…]`.

**Результат**:

- `a` получает путь `020.<segment>`;
- `a1` получает путь `020.<segment>.001`;
- `a1x` получает путь `020.<segment>.001.001`.

**Внутренние шаги** (`dragstructure_apply_order`):

1. Собрать `movingIds = {a, a1, a1x}` (корень + все потомки через `LIKE '010.%'`).
2. Все их старые пути исключаются из `usedPaths`.
3. Для `a` назначается `candidate = "020.<next>"`.
4. `walkChildren(a, "020.<next>")` рекурсивно назначает пути детям.

#### 6.3.5. Перемещение внутрь собственного потомка (запрещено)

**Действие**: перетащить `a` (path `010`) в `a1` (path `010.001`) — это создало бы цикл.

**Результат**: `dragstructure_validate_move()` возвращает ошибку `Cannot move category into its own descendant`, AJAX отвечает `{success:false}`, JS вызывает `alert()` и `location.reload()`.

**Проверка**:

```php
if (strpos($parentPath . '.', $childPath . '.') === 0) {
    return 'Cannot move category into its own descendant';
}
```

Здесь `parentPath = "010.001"`, `childPath = "010"`. После конкатенации: `"010.001."` начинается с `"010."` → ошибка.

#### 6.3.6. Перемещение в самого себя (запрещено)

`in_array($parentId, $order, true)` — если id перемещаемого узла совпадает с id нового родителя, операция отклоняется с `Cannot move category into itself`.

### 6.4. Порядок сортировки в UI (визуальный)

Фронтенд (JS в шаблоне) строит дерево по `CATS_JSON`:

```javascript
function buildByParent(cats) {
    const byParent = {};
    cats.forEach(c => {
        const key = c.parentPath || '';
        (byParent[key] = byParent[key] || []).push(c);
    });
    Object.keys(byParent).forEach(k => {
        byParent[k].sort((a, b) => a.path.localeCompare(b.path, undefined, { numeric: true }));
    });
    return byParent;
}
```

**Что делает `localeCompare(…, {numeric: true})`:**

- Строковое сравнение с учётом чисел: `"010"` < `"020"`, `"020"` < `"100"`.
- Без `{numeric: true}` сортировка была бы лексикографической по байтам, что для путей с ведущими нулями часто совпадает, но для длинных путей может отличаться.
- Использование `numeric:true` гарантирует, что `"010.002"` идёт после `"010.001"`.

**Почему сортировка делается ещё раз на клиенте, а не просто по порядку из JSON?**

- JSON уже приходит отсортированным (`ORDER BY structure_path ASC`), но
- **после перетаскивания** клиент обновляет `parentPath`-и, и порядок в массиве может временно разойтись с истинным. Повторная сортировка на клиенте гарантирует корректное отображение.

### 6.5. Порядок сортировки в БД и кеше

**В БД** — `ORDER BY structure_path ASC, structure_code ASC`. Поле `structure_code` — вторичный ключ сортировки, чтобы обеспечить детерминизм при равенстве путей (не должно случаться, но подстраховка).

**В кеше** — `cot_load_structure()` читает ту же таблицу с тем же порядком и складывает в `Cot::$structure[$area]` — ассоциативный массив по `code`, но **порядок итерации** сохраняется как порядок строк в SQL-результате. Соответственно, итерация `foreach (Cot::$structure[$area] as $code => $cat)` идёт в порядке `structure_path`.

### 6.6. Полный поток данных при сортировке

Разберём полный «жизненный цикл» одного перетаскивания:

**Шаг 1. Пользователь отпускает мышь над новым контейнером**

`SortableJS.onEnd` вызывается. `evt.to` — целевой контейнер, `evt.item` — перемещаемый элемент.

**Шаг 2. JS собирает данные**

```javascript
const toEl = evt.to;
const parentId = parseInt(toEl.dataset.parentId || '0', 10);
const order = Array.from(toEl.children)
    .filter(n => n.classList.contains('category-item'))
    .map(n => parseInt(n.dataset.id, 10));
```

**Шаг 3. JS формирует POST**

```javascript
const body = new URLSearchParams();
body.set('x', xToken);
body.set('ext', ext);
body.set('parent_id', parentId);
order.forEach(id => body.append('order[]', id));
```

`order[]` уходит массивом (не строкой `"1,2,3"`) — это критично для PHP.

**Шаг 4. AJAX-обработчик принимает**

`dragstructure.ajax.php`:

```php
$ext      = cot_import('ext', 'P', 'ALP');
$order    = cot_import('order', 'P', 'ARR');
$parentId = (int) cot_import('parent_id', 'P', 'INT');
```

**Шаг 5. Санитайз**

```php
$order = array_values(array_unique(array_map('intval', $order)));
$order = array_values(array_filter($order, fn($v) => $v > 0));
```

**Шаг 6. Валидация**

`dragstructure_validate_move()`:

- проверка `empty($order)`;
- проверка существования всех id;
- проверка существования `parentId`;
- проверка «не в себя» и «не в потомка».

**Шаг 7. Применение (транзакция)**

`dragstructure_apply_order()` — тяжёлая функция, разбираемая в разделе 9.

**Шаг 8. Очистка кеша**

```php
if (Cot::$cache) {
    Cot::$cache->clear();
}
```

**Шаг 9. Лог**

```php
cot_log(
    "Structure. Drag&drop reorder in '$ext' (parent: $parentId)",
    'adm',
    'structure',
    'update'
);
```

**Шаг 10. Commit**

```php
Cot::$db->commit();
```

**Шаг 11. Ответ**

```php
$response = [
    'success'    => true,
    'message'    => Cot::$L['dragstructure_saved'],
    'categories' => dragstructure_get_categories($ext),
];
```

**Шаг 12. Клиент перерисовывает дерево**

```javascript
if (Array.isArray(data.categories)) {
    currentCats = data.categories;
    render(currentCats);
} else {
    location.reload();
}
```

Ключевое преимущество: клиенту **не нужно** перезагружать страницу — он получает свежий `CATS_JSON` и перерисовывает DOM по актуальным путям из БД.

### 6.7. Правила и рекомендации по сортировке

**Правило 1. Не редактируйте `structure_path` вручную.**

Любая правка `structure_path` через phpMyAdmin или прямой SQL ломает кеш `Cot::$structure` до следующего запроса. Плагин делает это атомарно (транзакция + `clear()`).

**Правило 2. Используйте нормализацию с умом.**

Кнопка «Нормализовать» **обнуляет всю иерархию** — все категории становятся корневыми. Это инструмент **восстановления**, а не повседневной работы. Применяйте только если:
- пути разрушены (дубликаты, слипшиеся);
- структура была импортирована с ошибками;
- после сбоя предыдущей версии плагина.

**Правило 3. Шаг 10 у корней — не случайность.**

Это запас для будущих вставок. Если у вас 5 корневых категорий, их пути будут `010`, `020`, `030`, `040`, `050` — оставляя место для `015`, `025` и т.д.

**Правило 4. Три уровня — практический предел.**

Cotonti физически поддерживает любую вложенность, но UI навигации (хлебные крошки, URL) становится неочевидным после 3–4 уровней. Плагин позволяет больше, но это редко оправдано.

**Правило 5. Порядок влияет на хлебные крошки и меню.**

`cot_structure_buildpath()` читает `Cot::$structure[$area][$code]['path']` и разбивает по точкам, строя ссылки в порядке следования. Порядок в дереве = порядок в крошках.

**Правило 6. Изменения не откатываются.**

Плагин не ведёт историю перемещений и не поддерживает undo/redo. Если перемещение случайно — восстанавливайте вручную, зная желаемый итоговый порядок.

### 6.8. Таблица соответствия «действие → SQL-результат»

| Действие в UI | Изменяемые строки | Пример перехода пути |
|---|---|---|
| Перестановка детей `[A,B]` → `[B,A]` | 2 (A, B) | `010.001` ↔ `010.002` |
| Спуск в родителя | 1 + все потомки | `030` → `010.005` |
| Подъём в корень | 1 + все потомки | `010.005` → `060` |
| Перемещение в другого родителя | 1 + все потомки | `010.005` → `020.003` |
| Перемещение пустой категории | 1 | `030` → `040` |
| Нормализация области | все N строк | `001.005.001` → `010` |

## 7. Компоненты плагина — детальный разбор

### 7.1. `dragstructure.setup.php`

**Роль**: метаданные плагина и права по умолчанию.

**Содержимое блока `[BEGIN_COT_EXT]`:**

```
Code=dragstructure                     # Уникальный код
Name=Drag & Drop Structure             # Отображаемое имя
Category=administration                # Категория в списке
Description=…                          # Описание
Version=2.0.0
Date=2026-10-22
Author=webitproff
Copyright=(c) 2026 webitproff
Notes=

Auth_guests=R                          # Базовое право для гостей
Lock_guests=12345A                     # Заблокированные маски для гостей
Auth_members=RW                        # Базовое право для пользователей
Lock_members=12345A                    # Заблокированные маски
Requires_modules=                      # Зависимости от модулей (нет)
Requires_plugins=                      # Зависимости от плагинов (нет)
Recommends_modules=
Recommends_plugins=
[END_COT_EXT]
```

**Что важно знать:**

- **`Requires_modules=` пустой** — плагин формально не зависит ни от одного модуля. Но практически работает только если в системе есть хотя бы одна область структуры (иначе `cot_die_message(404)`).
- **`Category=administration`** — плагин появляется в разделе «Администрирование» списка расширений.
- **Права `R`/`W`** при активации записываются в таблицу `*_auth`, но реальный доступ всё равно контролируется в `tools.php` (см. раздел 10).

### 7.2. `dragstructure.tools.php`

**Роль**: точка входа админ-страницы. Подключается через хук `tools`.

**Поток выполнения:**

```
1. defined('COT_CODE') or die
2. require cot_incfile('dragstructure', 'plug')     ← API
3. require cot_langfile('dragstructure', 'plug')    ← локализация
4. cot_block(cot_auth('admin','a') || cot_auth('plug','dragstructure','A'))
5. $extensionsWithStructure = cot_getExtensionsWithStructure()
6. $ext = cot_import('ext', 'G', 'ALP')
7. if empty($ext) — взять первый из списка
8. if empty($extensionsWithStructure) — cot_die_message(404)
9. $t = new XTemplate(cot_tplfile('dragstructure.tools', 'plug', true))
10. Заголовок, adminPath
11. if ($a === 'normalize') — cot_check_xg(); normalize(); message(); redirect()
12. $categories = dragstructure_get_categories($ext)
13. $t->assign([EXT, EXT_LIST, FORM_ACTION, X_TOKEN, AJAX_URL, CATS_JSON, NORMALIZE_URL])
14. if empty($categories) — parse('MAIN.NO_CATS')
15. cot_display_messages($t)
16. $t->parse('MAIN')
17. $pluginBody = $t->text('MAIN')
```

**Ключевые точки:**

#### 7.2.1. Проверка прав

```php
cot_block(cot_auth('admin', 'a') || cot_auth('plug', 'dragstructure', 'A'));
```

- `cot_auth('admin', 'a')` — право администратора на раздел `admin`.
- `cot_auth('plug', 'dragstructure', 'A')` — право `A` (admin) на сам плагин.

`cot_block(false)` (если оба `false`) вызывает `cot_redirect` на страницу 403.

#### 7.2.2. Выбор области

```php
$ext = cot_import('ext', 'G', 'ALP');
if (empty($ext) || !in_array($ext, $extensionsWithStructure, true)) {
    $ext = !empty($extensionsWithStructure) ? $extensionsWithStructure[0] : '';
}
if ($ext === '') {
    cot_die_message(404, true, Cot::$L['dragstructure_no_ext']);
}
```

**Логика:**

- Параметр `ext` в URL (`?ext=page`) должен быть валидным кодом расширения.
- Список валидных расширений берётся из `cot_getExtensionsWithStructure()` — это расширения, объявившие хук `structure.extensions`.
- Если `ext` пуст — берётся первый из списка (обычно это самый активный модуль).
- Если список пуст — `404`.

**Почему `ALP`-фильтр?** `ALP` = «alphabetic» — пропускает только латиницу/цифры/`_`, что исключает инъекции в `$ext` на уровне URL-параметра.

#### 7.2.3. Нормализация

```php
if ($a === 'normalize') {
    cot_check_xg();
    $updated = dragstructure_normalize($ext);
    cot_message(cot_rc('dragstructure_normalized', ['count' => $updated]));
    cot_redirect(cot_url('admin', ['m' => 'other', 'p' => 'dragstructure', 'ext' => $ext], '', true));
}
```

- `cot_check_xg()` — проверка XSS-токена (обязательна для GET-действий).
- Редирект **убирает** `a=normalize` из URL, чтобы F5 не выполнил действие повторно.

#### 7.2.4. Присвоение тегов

```php
$t->assign([
    'EXT'           => $ext,
    'EXT_LIST'      => cot_selectbox($ext, 'ext', $extensionsWithStructure, $extensionsWithStructure, false, 'onchange="this.form.submit()"'),
    'FORM_ACTION'   => cot_url('admin', ['m' => 'other', 'p' => 'dragstructure', 'ext' => $ext]),
    'X_TOKEN'       => Cot::$sys['xk'],
    'AJAX_URL'      => cot_url('plug', ['r' => 'dragstructure']),
    'CATS_JSON'     => json_encode($categories, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT),
    'NORMALIZE_URL' => cot_url('admin', ['m' => 'other', 'p' => 'dragstructure', 'ext' => $ext, 'a' => 'normalize', 'x' => Cot::$sys['xk']]),
]);
```

**Ключевые теги:**

| Тег | Источник | Назначение |
|---|---|---|
| `EXT` | Выбранная область | `data-ext` в корневом `<div>` |
| `EXT_LIST` | `cot_selectbox()` | `<select>` для переключения |
| `FORM_ACTION` | `cot_url('admin', …)` | action формы |
| `X_TOKEN` | `Cot::$sys['xk']` | CSRF-токен для AJAX |
| `AJAX_URL` | `cot_url('plug', ['r' => 'dragstructure'])` | endpoint AJAX |
| `CATS_JSON` | `json_encode($categories, JSON_HEX_*)` | Данные для JS |
| `NORMALIZE_URL` | `cot_url(…, 'a' => 'normalize', 'x' => …)` | Ссылка на нормализацию |

**Почему `JSON_HEX_*` флаги?** Это защита от XSS: если в `title`/`desc` попадёт `<script>`, стандартный `json_encode` вернёт валидный JSON, но при вставке в `<script>` через `let currentCats = {CATS_JSON};` могут возникнуть проблемы. Флаги `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT` экранируют `<`, `>`, `&`, `'`, `"` в Unicode-последовательности, что делает вставку безопасной.

### 7.3. `dragstructure.tools.tpl`

**Роль**: HTML-каркас админ-страницы + встроенный JS для drag-and-drop.

**Основные блоки:**

- `MAIN` — корневой блок (обязателен).
- `NO_CATS` — предупреждение о пустой области (парсится условно).

**Структура DOM:**

```html
<div id="drag-structure"
     data-ext="{EXT}"
     data-x="{X_TOKEN}"
     data-ajax-url="{AJAX_URL}">
    <div id="category-tree" class="list-group" data-parent-id="0"></div>
    <!-- BEGIN: NO_CATS -->
    <div class="alert alert-info">{PHP.L.dragstructure_no_cats}</div>
    <!-- END: NO_CATS -->
</div>
```

- `#drag-structure` — корень, хранит `data-ext`, `data-x`, `data-ajax-url`.
- `#category-tree` — контейнер корневого уровня, `data-parent-id="0"`.

**Встроенный JS:**

```javascript
(function () {
    const root = document.getElementById('drag-structure');
    if (!root) return;

    const ext     = root.dataset.ext;
    const xToken  = root.dataset.x;
    const ajaxUrl = root.dataset.ajaxUrl;
    const rootEl  = document.getElementById('category-tree');

    let currentCats = {CATS_JSON};

    function buildByParent(cats) { … }
    function buildNode(cat) { … }
    function render(cats) { … }
    function initSortable(el) { … }

    render(currentCats);
})();
```

**Ключевые функции JS:**

#### `buildByParent(cats)`

Группирует категории по `parentPath` и сортирует каждую группу:

```javascript
byParent[k].sort((a, b) => a.path.localeCompare(b.path, undefined, { numeric: true }));
```

`numeric: true` обеспечивает корректное сравнение числовых сегментов.

#### `buildNode(cat)`

Создаёт DOM-узел:

```html
<div class="list-group-item category-item" data-id="123">
    <div class="d-flex align-items-center">
        <i class="fa-solid fa-grip-vertical me-2 text-muted category-handle"></i>
        <div class="flex-grow-1">
            <code class="me-2">010.001</code>
            <strong>news</strong> — Новости
        </div>
    </div>
    <div class="category-children" data-parent-id="123"></div>
</div>
```

- `.category-handle` — единственная «ручка», за которую можно тянуть (правило `handle: '.category-handle'` в SortableJS).
- `.category-children` — контейнер для детей с `data-parent-id` = id текущей категории.

**Важно**: `title`, `desc`, `code` вставляются через конкатенацию строк. Сервер уже прогнал их через `htmlspecialchars` в `dragstructure_get_categories`? **Нет** — в текущей реализации `dragstructure_get_categories()` возвращает «сырые» значения. Это потенциальная XSS-уязвимость на клиенте, если в `title` попадёт `<script>`. Однако:

- `CATS_JSON` экранируется `JSON_HEX_TAG` — это защищает от инъекции в `<script>`.
- При вставке в `innerHTML` через конкатенацию `htmlspecialchars` не применяется, что в теории позволяет XSS через данные БД.

**Рекомендация для сопровождения**: при следующей ревизии плагина добавить в JS экранирование полей (`escapeHtml()`) или в `dragstructure_get_categories()` применять `htmlspecialchars` (см. раздел 14).

#### `render(cats)`

Полная перерисовка дерева:

```javascript
function render(cats) {
    rootEl.innerHTML = '';
    const byParent = buildByParent(cats);
    function walk(parentPath, container) {
        (byParent[parentPath] || []).forEach(cat => {
            const node = buildNode(cat);
            container.appendChild(node);
            walk(cat.path, node.querySelector('.category-children'));
        });
    }
    walk('', rootEl);
    initSortable(rootEl);
}
```

**Замечание**: `render()` вызывается при каждом успешном AJAX-ответе — это простое и надёжное решение (нет частичных обновлений, которые могли бы «разъехаться» с БД).

#### `initSortable(el)`

Рекурсивная инициализация SortableJS на корне и всех `.category-children`:

```javascript
new Sortable(el, {
    group: { name: 'categories', pull: true, put: true },
    handle: '.category-handle',
    animation: 200,
    forceFallback: true,
    fallbackOnBody: true,
    swapThreshold: 0.5,
    emptyInsertThreshold: 5,
    ghostClass: 'sortable-ghost',
    chosenClass: 'sortable-chosen',
    onEnd(evt) { … }
});
el.querySelectorAll(':scope > .category-item > .category-children').forEach(initSortable);
```

**Параметры:**

- `group: { name: 'categories', pull: true, put: true }` — все контейнеры принадлежат одной группе и могут обмениваться элементами.
- `forceFallback: true` — обход проблем нативного HTML5 drag во вложенных контейнерах.
- `fallbackOnBody: true` — «призрак» рендерится в body, что избегает обрезания.
- `swapThreshold: 0.5` — порог переключения.
- `emptyInsertThreshold: 5` — позволяет бросить в пустой контейнер.
- `ghostClass`, `chosenClass` — CSS-классы для визуальной обратной связи.

#### `onEnd(evt)`

Обработчик завершения перетаскивания:

```javascript
onEnd(evt) {
    const toEl = evt.to;
    const parentId = parseInt(toEl.dataset.parentId || '0', 10);
    const order = Array.from(toEl.children)
        .filter(n => n.classList.contains('category-item'))
        .map(n => parseInt(n.dataset.id, 10));

    const body = new URLSearchParams();
    body.set('x', xToken);
    body.set('ext', ext);
    body.set('parent_id', parentId);
    order.forEach(id => body.append('order[]', id));

    fetch(ajaxUrl, {
        method: 'POST',
        headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
        body
    })
    .then(r => r.json())
    .then(data => {
        if (!data.success) {
            alert(data.message || 'Error');
            location.reload();
            return;
        }
        if (Array.isArray(data.categories)) {
            currentCats = data.categories;
            render(currentCats);
        } else {
            location.reload();
        }
    })
    .catch(err => {
        console.error(err);
        alert('Network error');
        location.reload();
    });
}
```

**Важные решения:**

- `order.forEach(id => body.append('order[]', id))` — **критично** для PHP: `order[]` даёт массив, `order` даст строку.
- На ошибку — `location.reload()`: DOM уже разъехался с БД после перетаскивания, откат вручную бессмысленен.
- На успех — `render(currentCats)` с новым `data.categories` из ответа.

### 7.4. `dragstructure.ajax.php`

**Роль**: AJAX-обработчик. Подключается через хук `ajax` в `plug.php?r=dragstructure`.

**Структура:**

```php
defined('COT_CODE') or die('Wrong URL.');

// Подавляем любой вывод ошибок
ini_set('display_errors', '0');
error_reporting(0);

// Буферизация
ob_start();

$response = ['success' => false, 'message' => 'Unknown error'];

try {
    require_once cot_incfile('dragstructure', 'plug');
    require_once cot_langfile('dragstructure', 'plug');

    if (!cot_auth('admin', 'a') && !cot_auth('plug', 'dragstructure', 'A')) {
        ob_end_clean();
        http_response_code(403);
        header('Content-Type: application/json; charset=utf-8');
        echo json_encode(['success' => false, 'message' => 'Forbidden']);
        exit;
    }

    if (!cot_check_xp()) {
        ob_end_clean();
        http_response_code(400);
        header('Content-Type: application/json; charset=utf-8');
        echo json_encode(['success' => false, 'message' => 'Invalid CSRF token']);
        exit;
    }

    $ext      = cot_import('ext', 'P', 'ALP');
    $order    = cot_import('order', 'P', 'ARR');
    $parentId = (int) cot_import('parent_id', 'P', 'INT');

    if ($ext === '' || !is_array($order) || empty($order)) {
        ob_end_clean();
        http_response_code(400);
        header('Content-Type: application/json; charset=utf-8');
        echo json_encode(['success' => false, 'message' => 'Invalid input']);
        exit;
    }

    // Fallback на строку "1,2,3"
    if (!is_array($order)) {
        $order = explode(',', (string) $order);
    }
    $order = array_values(array_unique(array_map('intval', $order)));
    $order = array_values(array_filter($order, fn($v) => $v > 0));

    if (empty($order)) {
        ob_end_clean();
        http_response_code(400);
        header('Content-Type: application/json; charset=utf-8');
        echo json_encode(['success' => false, 'message' => 'Empty order']);
        exit;
    }

    $error = dragstructure_move($ext, $order, $parentId);

    if ($error !== null) {
        $response = ['success' => false, 'message' => $error];
    } else {
        $response = [
            'success'    => true,
            'message'    => Cot::$L['dragstructure_saved'],
            'categories' => dragstructure_get_categories($ext),
        ];
    }
} catch (Throwable $e) {
    $response = ['success' => false, 'message' => $e->getMessage()];
}

ob_end_clean();
header('Content-Type: application/json; charset=utf-8');
echo json_encode($response);
exit;
```

**Ключевые технические решения:**

#### 7.4.1. `ini_set('display_errors', '0')` + `error_reporting(0)`

Если PHP-предупреждение (например, `Notice: Undefined index`) попадёт в поток до `echo json_encode()`, ответ станет невалидным JSON. Подавление обязательно для AJAX-обработчиков.

#### 7.4.2. `ob_start()` + `ob_end_clean()`

Даже если какой-то BOM-символ попадёт в начало ответа (частая проблема с UTF-8 файлами), `ob_end_clean()` его отбросит.

#### 7.4.3. `cot_check_xp()` — CSRF

Проверяет наличие и валидность POST-поля `x`, которое совпадает с `Cot::$sys['xk']`. Механизм встроен в Cotonti.

#### 7.4.4. Fallback для `order`

```php
if (!is_array($order)) {
    $order = explode(',', (string) $order);
}
```

На случай, если клиент (или другая интеграция) отправит `order="1,2,3"` вместо массива. Основной клиент отправляет массив, но fallback повышает устойчивость.

#### 7.4.5. Санитайз

```php
$order = array_values(array_unique(array_map('intval', $order)));
$order = array_values(array_filter($order, fn($v) => $v > 0));
```

- `array_map('intval', …)` — приведение к int (защита от `"1abc"` и `"' OR '1'='1"`);
- `array_unique()` — устранение дублей;
- `array_filter(fn($v) => $v > 0)` — отбрасывание `0` и отрицательных;
- `array_values()` — переиндексация.

#### 7.4.6. Коды HTTP-ответов

| Ситуация | HTTP-код |
|---|---|
| Нет прав | 403 |
| Невалидный CSRF | 400 |
| Невалидный ввод | 400 |
| Пустой order | 400 |
| Успех | 200 (по умолчанию) |
| Исключение в try | 200 (тело — `{success:false}`, чтобы JS обработал) |

Формально код 500 не выставляется в `catch`, но `{success:false}` информирует клиент.

### 7.5. `inc/dragstructure.functions.php`

**Роль**: бизнес-логика плагина. Пять функций:

1. `dragstructure_get_categories(string $ext): array`
2. `dragstructure_index_by_id(array $categories): array`
3. `dragstructure_validate_move(array $byId, array $order, int $parentId): ?string`
4. `dragstructure_apply_order(string $ext, array $byId, array $order, int $parentId): void`
5. `dragstructure_move(string $ext, array $order, int $parentId): ?string`
6. `dragstructure_normalize(string $ext): int`

#### 7.5.1. `dragstructure_get_categories()`

Читает `*_structure` для области, возвращает плоский массив:

```php
[
    [
        'id'         => 1095,
        'code'       => 'site-administration',
        'title'      => 'Администрирование сайтов',
        'desc'       => 'Управление и поддержка веб-сайтов.',
        'path'       => '001',
        'parentPath' => '',
    ],
    // …
]
```

**SQL**: `SELECT structure_id, structure_code, structure_path, structure_title, structure_desc FROM *_structure WHERE structure_area = ? ORDER BY structure_path ASC, structure_code ASC`.

**Особенности:**

- `parentPath` вычисляется в PHP: `substr($path, 0, strrpos($path, '.'))`, если есть точка; иначе `''`.
- Все поля приводятся к ожидаемым типам (`int`, `string`).

#### 7.5.2. `dragstructure_index_by_id()`

Тривиальная индексация:

```php
$map = [];
foreach ($categories as $cat) {
    $map[$cat['id']] = $cat;
}
return $map;
```

Используется для быстрого поиска по `structure_id`.

#### 7.5.3. `dragstructure_validate_move()`

Проверяет три типа ошибок:

1. **Пустой `order`** → `'Empty order'`.
2. **Отсутствующие id** → `"Category #$id not found"` или `"Parent #$parentId not found"`.
3. **Циклы**:
   - «в себя»: `in_array($parentId, $order, true)` → `'Cannot move category into itself'`;
   - «в потомка»: `strpos($parentPath . '.', $childPath . '.') === 0` → `'Cannot move category into its own descendant'`.

**Важно**: проверка «order содержит предка и потомка» **не выполняется** — она ложно срабатывает при переносе между уровнями (узлы ещё хранят старые пути). Консистентность гарантируется в `dragstructure_apply_order()` через построение `childrenMap`.

#### 7.5.4. `dragstructure_apply_order()` — центральная функция

**Полный алгоритм:**

1. **`$parentPath`**: `$parentId > 0 ? $byId[$parentId]['path'] : ''`.

2. **Сбор `movingIds`** — все перемещаемые + их потомки:

   ```php
   $movingIds = array_flip($order);
   foreach ($order as $id) {
       $descendants = Cot::$db->query(
           'SELECT structure_id FROM ' . Cot::$db->structure . '
            WHERE structure_area = ? AND structure_path LIKE ?',
           [$ext, $byId[$id]['path'] . '.%']
       )->fetchAll();
       foreach ($descendants as $d) {
           $movingIds[(int) $d['structure_id']] = true;
       }
   }
   ```

3. **`usedPaths`** — все пути, кроме `movingIds`:

   ```php
   $usedPaths = [];
   foreach ($byId as $id => $cat) {
       if (!isset($movingIds[$id])) {
           $usedPaths[$cat['path']] = true;
       }
   }
   ```

   **Почему**: если `a` (path `010`) перемещается, его старый `010` не должен блокировать выбор `010` для другой категории.

4. **`pathToId`** — обратная карта `path → id`.

5. **`childrenMap`** — карта `parentId → [childId]` для перемещаемых:

   ```php
   $childrenMap = [];
   foreach ($byId as $id => $cat) {
       if (!isset($movingIds[$id])) {
           continue;
       }
       $pid = 0;
       if ($cat['parentPath'] !== '' && isset($pathToId[$cat['parentPath']])) {
           $pid = $pathToId[$cat['parentPath']];
       }
       $childrenMap[$pid][] = $id;
   }
   ```

6. **Назначение новых путей для `order`**:

   ```php
   $changes = [];
   $isRootParent = ($parentPath === '');
   $pos = 0;
   foreach ($order as $id) {
       $oldPath = $byId[$id]['path'];
       do {
           $pos++;
           $segment = $isRootParent
               ? sprintf('%03d', $pos * 10)
               : sprintf('%03d', $pos);
           $candidate = $isRootParent ? $segment : $parentPath . '.' . $segment;
       } while (isset($usedPaths[$candidate]));

       $usedPaths[$candidate] = true;
       $changes[$id] = ['old' => $oldPath, 'new' => $candidate];
   }
   ```

   - Корень: `010`, `020`, … (шаг 10).
   - Вложенный: `.001`, `.002`, … (шаг 1).
   - `while (isset($usedPaths[$candidate]))` — при коллизии с существующей категорией сдвигает `pos`.

7. **Рекурсивный `walkChildren`** для потомков:

   ```php
   $walkChildren = function (int $pid, string $parentPath) use (&$walkChildren, &$childrenMap, &$changes, &$byId, &$usedPaths) {
       $children = $childrenMap[$pid] ?? [];
       $pos = 0;
       foreach ($children as $childId) {
           if (isset($changes[$childId])) {
               continue;  // уже обработан в order
           }
           $oldPath = $byId[$childId]['path'];
           do {
               $pos++;
               $segment = sprintf('%03d', $pos);
               $candidate = $parentPath . '.' . $segment;
           } while (isset($usedPaths[$candidate]));

           $usedPaths[$candidate] = true;
           $changes[$childId] = ['old' => $oldPath, 'new' => $candidate];
           $walkChildren($childId, $candidate);
       }
   };

   foreach ($changes as $id => $info) {
       $walkChildren($id, $info['new']);
   }
   ```

8. **`dirty`** — только фактически изменяемые:

   ```php
   $dirty = [];
   foreach ($changes as $id => $info) {
       if ($info['old'] !== $info['new']) {
           $dirty[$id] = $info;
       }
   }
   if (empty($dirty)) {
       return;
   }
   ```

9. **Двухфазное применение**:

   ```php
   $tmpPrefix = '_t_' . bin2hex(random_bytes(6)) . '_';
   foreach ($dirty as $id => $info) {
       Cot::$db->update(Cot::$db->structure,
           ['structure_path' => $tmpPrefix . $id],
           'structure_id = ? AND structure_area = ?', [$id, $ext]);
   }
   foreach ($dirty as $id => $info) {
       Cot::$db->update(Cot::$db->structure,
           ['structure_path' => $info['new']],
           'structure_id = ? AND structure_area = ?', [$id, $ext]);
   }
   ```

   **Зачем две фазы**: если `structure_path` имеет UNIQUE-индекс (в текущей схеме Cotonti нет, но плагин защищается на будущее), прямой своп `010.001 ↔ 010.002` упадёт с duplicate key. Временные пути снимают проблему.

#### 7.5.5. `dragstructure_move()`

Полный сценарий с транзакцией:

```php
function dragstructure_move(string $ext, array $order, int $parentId): ?string
{
    $categories = dragstructure_get_categories($ext);
    if (empty($categories)) {
        return 'No categories in extension';
    }

    $byId = dragstructure_index_by_id($categories);

    $error = dragstructure_validate_move($byId, $order, $parentId);
    if ($error !== null) {
        return $error;
    }

    Cot::$db->beginTransaction();
    try {
        dragstructure_apply_order($ext, $byId, $order, $parentId);

        if (Cot::$cache) {
            Cot::$cache->clear();
        }

        cot_log(
            "Structure. Drag&drop reorder in '$ext' (parent: $parentId)",
            'adm',
            'structure',
            'update'
        );

        Cot::$db->commit();
        return null;
    } catch (Throwable $e) {
        Cot::$db->rollBack();
        return $e->getMessage();
    }
}
```

**Порядок операций критичен:**

1. **Валидация до транзакции** — быстрый отказ без нагрузки на БД.
2. **Транзакция** — все `UPDATE` либо применяются, либо откатываются.
3. **`cache->clear()`** внутри try — если кеш даст исключение, всё откатится.
4. **`cot_log()` внутри try** — если лог упадёт, изменения откатятся.
5. **`commit()`** — только после успешного лога.
6. **`rollBack()` в catch** — гарантия атомарности.

#### 7.5.6. `dragstructure_normalize()`

```php
function dragstructure_normalize(string $ext): int
{
    $rows = Cot::$db->query(
        'SELECT structure_id FROM ' . Cot::$db->structure . '
         WHERE structure_area = ?
         ORDER BY structure_id ASC',
        [$ext]
    )->fetchAll();

    $pos = 0;
    $updated = 0;
    foreach ($rows as $row) {
        $pos++;
        $newPath = sprintf('%03d', $pos * 10);
        $affected = Cot::$db->update(
            Cot::$db->structure,
            ['structure_path' => $newPath],
            'structure_id = ? AND structure_area = ? AND structure_path <> ?',
            [(int) $row['structure_id'], $ext, $newPath]
        );
        $updated += $affected;
    }

    if (Cot::$cache) {
        Cot::$cache->clear();
    }

    return $updated;
}
```

**Ключевые моменты:**

- Сортировка по `structure_id` — стабильная, не зависит от текущего состояния путей.
- Пути: `010`, `020`, `030`, … (шаг 10, ширина 3).
- Условие `structure_path <> ?` — не перезаписывает уже правильные пути (оптимизация + корректный `$affected`).
- **Не в транзакции** — в отличие от `dragstructure_move()`. Это осознанно: нормализация идемпотентна, если прервётся на середине, повторный запуск доведёт до конца.

## 9. Алгоритмы пересчёта путей

### 9.1. Сводка алгоритмов

| Функция | Назначение | Сложность |
|---|---|---|
| `dragstructure_get_categories()` | Выборка + нормализация | O(n) |
| `dragstructure_index_by_id()` | Индексация | O(n) |
| `dragstructure_validate_move()` | Валидация | O(n·m) где m — длина order |
| `dragstructure_apply_order()` | Пересчёт путей | O(n·d) где d — глубина |
| `dragstructure_move()` | Полный сценарий | O(n·d + n log n) |
| `dragstructure_normalize()` | Плоская нумерация | O(n) |

### 9.2. Псевдокод `dragstructure_apply_order`

```
FUNCTION apply_order(ext, byId, order, parentId):
    parentPath = (parentId > 0) ? byId[parentId].path : ""

    # Шаг 1. Найти перемещаемые + всех потомков
    movingIds = set(order)
    FOR id IN order:
        descendants = SELECT structure_id FROM structure
                      WHERE area = ext AND path LIKE byId[id].path + ".%"
        FOR d IN descendants:
            movingIds.add(d.structure_id)

    # Шаг 2. Собрать используемые пути
    usedPaths = { byId[id].path : id ∉ movingIds }

    # Шаг 3. Построить pathToId
    pathToId = { cat.path : id : ∀ id ∈ byId }

    # Шаг 4. Построить childrenMap
    childrenMap = {}
    FOR id, cat IN byId:
        IF id ∉ movingIds: CONTINUE
        pid = (cat.parentPath ≠ "" AND cat.parentPath ∈ pathToId)
              ? pathToId[cat.parentPath] : 0
        childrenMap[pid].add(id)

    # Шаг 5. Назначить новые пути для order
    changes = {}
    isRootParent = (parentPath == "")
    pos = 0
    FOR id IN order:
        oldPath = byId[id].path
        DO:
            pos++
            segment = isRootParent ? format("%03d", pos*10) : format("%03d", pos)
            candidate = isRootParent ? segment : parentPath + "." + segment
        WHILE candidate ∈ usedPaths
        usedPaths.add(candidate)
        changes[id] = {old: oldPath, new: candidate}

    # Шаг 6. Рекурсивно пересчитать потомков
    FUNCTION walkChildren(pid, parentPath):
        FOR childId IN childrenMap[pid]:
            IF childId ∈ changes: CONTINUE
            oldPath = byId[childId].path
            pos = 0
            DO:
                pos++
                segment = format("%03d", pos)
                candidate = parentPath + "." + segment
            WHILE candidate ∈ usedPaths
            usedPaths.add(candidate)
            changes[childId] = {old: oldPath, new: candidate}
            walkChildren(childId, candidate)

    FOR id, info IN changes:
        walkChildren(id, info.new)

    # Шаг 7. Отфильтровать неизменённые
    dirty = { id : info ∈ changes : info.old ≠ info.new }
    IF dirty IS EMPTY: RETURN

    # Шаг 8. Двухфазное применение
    tmpPrefix = "_t_" + random_hex(6) + "_"
    FOR id, info IN dirty:
        UPDATE structure SET path = tmpPrefix + id
        WHERE id = structure_id AND area = ext
    FOR id, info IN dirty:
        UPDATE structure SET path = info.new
        WHERE id = structure_id AND area = ext
```

### 9.3. Пример трассировки

**Дано:**

```
id=1  code=a     path=010         (корень)
id=2  code=a1    path=010.001     parentPath=010
id=3  code=a2    path=010.002     parentPath=010
id=4  code=a1x   path=010.001.001 parentPath=010.001
```

**Действие**: перестановка `[a1, a2]` → `[a2, a1]`, `parentId=1`, `order=[3, 2]`.

**Шаг 1.** `movingIds = {3, 2}`. Потомки `a2` (`path=010.002`) — нет. Потомки `a1` (`path=010.001`) — `a1x` (id 4). `movingIds = {3, 2, 4}`.

**Шаг 2.** `usedPaths = {"010"}` (только `a`).

**Шаг 3.** `pathToId = {"010": 1, "010.001": 2, "010.002": 3, "010.001.001": 4}`.

**Шаг 4.** `childrenMap`:
- `a1` (id 2): `parentPath = "010"`, pid = 1. → `childrenMap[1] += [2]`.
- `a2` (id 3): `parentPath = "010"`, pid = 1. → `childrenMap[1] += [3]`.
- `a1x` (id 4): `parentPath = "010.001"`, pid = 2. → `childrenMap[2] += [4]`.

**Шаг 5.** `parentPath = "010"`, `isRootParent = false`.
- `id = 3` (`a2`): `pos=1`, segment=`"001"`, candidate=`"010.001"`. Не в `usedPaths`. `changes[3] = {"010.002" → "010.001"}`. `usedPaths = {"010", "010.001"}`.
- `id = 2` (`a1`): `pos=2`, segment=`"002"`, candidate=`"010.002"`. Не в `usedPaths`. `changes[2] = {"010.001" → "010.002"}`. `usedPaths = {"010", "010.001", "010.002"}`.

**Шаг 6.** `walkChildren(3, "010.001")` — нет детей. `walkChildren(2, "010.002")`:
- `childId = 4` (`a1x`): `pos=1`, segment=`"001"`, candidate=`"010.002.001"`. Свободен. `changes[4] = {"010.001.001" → "010.002.001"}`.

**Шаг 7.** Все три изменения реальны, `dirty = {3, 2, 4}`.

**Шаг 8.** Фаза 1:
- `UPDATE` id=3 → `_t_abc123_3`
- `UPDATE` id=2 → `_t_abc123_2`
- `UPDATE` id=4 → `_t_abc123_4`

Фаза 2:
- `UPDATE` id=3 → `010.001`
- `UPDATE` id=2 → `010.002`
- `UPDATE` id=4 → `010.002.001`

**Результат:**

```
id=1  code=a     path=010
id=2  code=a1    path=010.002
id=3  code=a2    path=010.001
id=4  code=a1x   path=010.002.001
```

Порядок детей `010` в UI: `a2` (`010.001`) → `a1` (`010.002`) → `a1x` (`010.002.001`). Всё корректно.

### 9.4. Пограничные случаи алгоритма

#### 9.4.1. Перемещение в пустой `order` (после sanitize)

`dragstructure_validate_move` вернёт `'Empty order'` — до транзакции.

#### 9.4.2. Перемещение в нового родителя, где уже есть дети

Дети нового родителя не перемещаются — они сохраняют свои `path`. `usedPaths` будет содержать их пути, и алгоритм не назначит конфликтующие.

#### 9.4.3. Удалённая категория

`isset($byId[$id])` вернёт `false` → ошибка. Это защита от устаревшего DOM.

#### 9.4.4. Изменение `parentId` в полёте

Если между рендером и AJAX-запросом категория `parentId` была удалена — валидация вернёт `"Parent #N not found"`.

## 10. Безопасность: CSRF, XSS, права доступа

### 10.1. Права доступа

**Три уровня проверки:**

1. **Уровень плагина (`cot_auth('plug', 'dragstructure', 'A')`)** — глобальная настройка «кто имеет право на плагин». Управляется через `admin.php?m=rights`.
2. **Уровень администратора (`cot_auth('admin', 'a')`)** — стандартное право администратора сайта.
3. **Уровень action (внутри `tools.php`)** — `cot_block()` в начале файла.

`ajax.php` содержит **дублирующую** проверку:

```php
if (!cot_auth('admin', 'a') && !cot_auth('plug', 'dragstructure', 'A')) {
    http_response_code(403);
    echo json_encode(['success' => false, 'message' => 'Forbidden']);
    exit;
}
```

Это обязательно: AJAX-эндпоинт доступен напрямую через `plug.php?r=dragstructure`, без прохода через `tools.php`.

### 10.2. CSRF-защита

**Механизм Cotonti:**

- Токен `Cot::$sys['xk']` — 32-символьная строка, генерируемая при инициализации сессии.
- **GET-действия**: `cot_check_xg()` — проверяет `$_GET['x']`.
- **POST-действия**: `cot_check_xp()` — проверяет `$_POST['x']`.

**В плагине:**

- **Нормализация** (GET) — `cot_check_xg()` в `tools.php`.
- **AJAX reorder** (POST) — `cot_check_xp()` в `ajax.php`.
- **CSRF-токен передаётся в JS** через `data-x="{X_TOKEN}"` и добавляется в каждый POST.

**Что защищает:**

- Злоумышленник не может сконструировать POST-запрос с чужого сайта (нет доступа к `xk`).
- Ссылка `<a href="admin.php?m=other&p=dragstructure&a=normalize">` без `&x=…` не сработает.

### 10.3. XSS-защита

**Три уровня:**

1. **`JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT`** при `json_encode($categories)` — экранирует `<`, `>`, `&`, `'`, `"` в Unicode-последовательности, безопасные для вставки в `<script>`.

2. **`cot_import($ext, 'G', 'ALP')`** — фильтр ALP пропускает только `[a-zA-Z0-9_]`, что исключает инъекции в `$ext`.

3. **`array_map('intval', $order)`** — приведение id к int.

**Проблема (потенциальная):**

В JS `buildNode(cat)` значения `cat.title`, `cat.desc`, `cat.code` вставляются в `innerHTML` через конкатенацию:

```javascript
'<strong>' + cat.code + '</strong> — ' + cat.title +
(cat.desc ? '<div class="small text-muted">' + cat.desc + '</div>' : '')
```

Если в `title` содержится `<img src=x onerror=alert(1)>`, это сработает при рендере. **Рекомендация** для будущих версий: экранировать в JS или в `dragstructure_get_categories()` применять `htmlspecialchars()`.

**Текущее состояние**: риск **ограничен** тем, что редактировать `structure_title`/`structure_desc` могут только администраторы (через `admin.php?m=structure`), а `dragstructure` доступен той же категории пользователей. То есть XSS возможен только «сам себе» — снижает критичность, но не устраняет.

### 10.4. SQL-инъекции

Все запросы используют **prepared statements** через `Cot::$db->query($sql, $params)` (обёртка над PDO):

```php
Cot::$db->query(
    'SELECT … WHERE structure_area = ?',
    [$ext]
);
```

`$order` содержит int (после `array_map('intval', …)`), `$parentId` — int. Прямой конкатенации в SQL нет.

**Единственное исключение**: `LIKE ?` с параметром `$byId[$id]['path'] . '.%'` — но `path` берётся из БД, а не из пользовательского ввода.

### 10.5. Защита от параллельных изменений

**Сценарий**: два администратора одновременно редактируют структуру.

**Проблема**: если админ A удалил категорию `X`, а админ B в этот момент пытается её переместить, `dragstructure_validate_move` вернёт `"Category #N not found"` — B получит alert и `location.reload()`.

**Транзакция**: `dragstructure_move` использует `beginTransaction`/`commit`, что даёт изоляцию на уровне БД. При параллельном изменении один из запросов откатится.

**Ограничение**: нет механизма блокировок (row-level locking через `SELECT … FOR UPDATE`). Очень быстрый параллельный конфликт теоретически возможен, но `structure_path` редко имеет UNIQUE-индекс, а `structure_id` — первичный ключ, и UPDATE'ы разных строк не конфликтуют.

## 12. Интеграция с ядром Cotonti

### 12.1. Хуки

Плагин использует **два хука**:

| Хук | Файл | Точка входа |
|---|---|---|
| `tools` | `dragstructure.tools.php` | `admin.php?m=other&p=dragstructure` |
| `ajax` | `dragstructure.ajax.php` | `plug.php?r=dragstructure` |

**Почему `tools`, а не `admin`?**

Хук `admin` создаёт пункт в меню «Администрирование», а `tools` — в «Инструменты». Плагин — инструмент, а не самостоятельный раздел. Это архитектурно корректнее.

**Почему `ajax`, а не `standalone`?**

`ajax` подключается через `plug.php?r=dragstructure` без рендера страницы, что идеально для JSON-ответов. `standalone` был бы излишним.

### 12.2. `cot_getExtensionsWithStructure()`

```php
function cot_getExtensionsWithStructure()
{
    static $extensionsWithStructure = [];
    static $loaded = false;

    if ($loaded) return $extensionsWithStructure;

    /* === Hook === */
    foreach (cot_getextplugins('structure.extensions') as $pl) {
        include $pl;
    }
    /* ===== */

    $loaded = true;
    return $extensionsWithStructure;
}
```

Это **точка расширения**: каждый модуль/плагин, желающий участвовать в структуре, объявляет:

```php
$extensionsWithStructure[] = 'my_module';
```

через свой плагин на хук `structure.extensions`. `dragstructure` подхватывает этот список.

**Следствие**: если какое-то расширение не объявило хук, оно **не появится** в выпадающем списке плагина. Это защищает от попытки редактировать структуру области, не поддерживающей её.

### 12.3. `*_structure` и `*_pages`

Плагин **не трогает** `*_pages` (и другие контентные таблицы). `structure_count` пересчитывается модулями через функции `cot_<area>_sync()`, которые плагин **не вызывает** — это ответственность `admin.php?m=structure&a=resyncall`.

**Следствие**: после перетаскивания `structure_count` не меняется (что логично — количество элементов в категории не зависит от её позиции).

### 12.4. Кеш

`Cot::$cache->clear()` в `dragstructure_move` и `dragstructure_normalize` полностью сбрасывает кеш Cotonti (файловый, APC, memcached — зависит от конфигурации).

**Почему полный сброс**: `cot_load_structure()` кешируется на уровне `$structure` в `Cot::$structure`, плюс есть `cot_cache_*` механизмы в различных модулях. Точечный сброс (`delete('structure')`) не покрыл бы все зависимые кеши. Полный `clear()` — гарантия консистентности.

**Цена**: на крупных сайтах полный сброс кеша после каждой перестановки может быть заметен. Если это станет проблемой — оптимизация: сбрасывать только `structure`-related ключи.

### 12.5. Логирование

`cot_log()` пишет в `*_logger`:

```
Structure. Drag&drop reorder in 'page' (parent: 0)
Structure. Drag&drop reorder in 'market' (parent: 22)
```

Просмотр: `admin.php?m=logger`.

**Что не логируется:**

- Нормализация (только через `cot_message`, в UI).
- Неуспешные попытки (валидация отклоняет до транзакции).

**Рекомендация для аудита**: добавить `cot_log(…)` в блок `a === 'normalize'` в `tools.php`, если требуется полный аудит.

## 13. Сценарии использования

### 13.1. Типовой сценарий: реорганизация каталога

**Дано**: 200+ категорий в `market`, часть неактуальна, часть — в неверных родителях.

**Шаги:**

1. Открыть `admin.php?m=other&p=dragstructure&ext=market`.
2. Убедиться, что в выпадающем списке выбрано «market».
3. Перетащить группы категорий в правильных родителей.
4. Проверить `data.categories` в ответе AJAX — все `path` пересчитаны.
5. Зайти на публичную часть — проверить, что крошки и меню корректны.

**Результат**: 200 UPDATE-запросов, один вызов `cache->clear()`, одна запись в логе (фактически — по одной на каждое перетаскивание).

### 13.2. Сценарий: восстановление после сбоя

**Дано**: в `structure_path` дубликаты (`001` встречается дважды) — ранее сломали.

**Шаги:**

1. Нажать «Нормализовать пути».
2. Подтвердить в `confirm()`.
3. Получить `Нормализовано категорий: 200` (или сколько было изменено).
4. Все категории стали корневыми (`010`, `020`, …).
5. Вручную расставить иерархию перетаскиванием.

**Важно**: иерархия **не восстанавливается** — только плоский список. Это документированное поведение.

### 13.3. Сценарий: миграция с другой CMS

**Дано**: импорт 500 категорий из CSV/XML в `*_structure` с `path` = `0`, `0.0` и т.п.

**Шаги:**

1. Импорт — все `path` условно «плоские», но с некорректными значениями.
2. «Нормализовать пути» — все станут `010`, `020`, …
3. Если структура важна — предварительно собрать карту «code → parentCode» и воссоздать иерархию либо через `admin.php?m=structure`, либо написав скрипт поверх `dragstructure_move`.

### 13.4. Сценарий: тестирование перед запуском

**Дано**: перед публикацией нужно проверить разные варианты иерархии.

**Шаги:**

1. Перетащить категории в один вариант.
2. Открыть публичную часть — оценить UX (крошки, меню).
3. Вернуться в админку — перетащить в другой вариант.
4. Повторять до финала.

**Плюс**: `cache->clear()` + `cot_load_structure()` гарантируют, что публичная часть видит актуальные пути сразу после перетаскивания.

### 13.5. Сценарий: аудит изменений

**Дано**: несколько администраторов с доступом к плагину.

**Шаги:**

1. Все перетаскивания логируются через `cot_log`.
2. `admin.php?m=logger` → фильтр по группе `adm`, типу `structure`.
3. Каждая запись содержит: `area`, `parent_id`, дату, IP, пользователя.

**Ограничение**: не логируется, какие именно id были переставлены — только факт. Для детального аудита нужно расширение `cot_log()`.

## 14. Ограничения и граничные случаи

### 14.1. Технические ограничения

| Ограничение | Причина | Обход |
|---|---|---|
| Максимум 3 уровня на практике | UI-навигация | Не рекомендуется уходить глубже |
| Нет undo/redo | Не реализовано | Восстанавливать вручную |
| Нет истории перемещений | Не реализовано | Смотреть `cot_log` |
| Нормализация теряет иерархию | Алгоритм плоской нумерации | Не использовать без необходимости |
| Требуется JS | SortableJS + fetch | Не работает без JS |
| CDN SortableJS | Подключён в шаблоне | Заменить на локальную копию |
| Потенциальный XSS через `title`/`desc` | См. раздел 10.3 | Экранировать в JS |

### 14.2. Граничные случаи

#### 14.2.1. Пустая область

`dragstructure_get_categories` возвращает `[]` → парсится блок `NO_CATS` → в UI предупреждение. Плагин работает корректно.

#### 14.2.2. Область с одной категорией

Работает. Перетаскивать некуда, но UI рендерится.

#### 14.2.3. Область с очень глубокой иерархией (10+ уровней)

Работает, но `render()` рекурсивно углубляется, что может дать проблемы с производительностью на клиенте. Cotonti физически поддерживает.

#### 14.2.4. Категория с иконкой `structure_icon`

Иконка **не отображается** в UI плагина — только `path`, `code`, `title`, `desc`. Это ограничение UI.

#### 14.2.5. Заблокированная категория (`structure_locked=1`)

Плагин **не блокирует** перемещение. `structure_locked` — это «нельзя создавать/редактировать контент», но не «нельзя перемещать».

#### 14.2.6. Категория `all`

В Cotonti есть виртуальная категория `all` — она **не хранится** в `*_structure`, плагин её не видит. Никакого конфликта.

#### 14.2.7. Категория `system`

Служебная категория (`page.system`) — плагин её видит и может перемещать. **Не рекомендуется** — `system` обычно содержит служебные страницы.

#### 14.2.8. Коллизия UNIQUE-индекса

Если у `structure_path` есть UNIQUE-индекс (не в штатной схеме), двухфазное применение решает проблему.

#### 14.2.9. Одновременные перемещения

Транзакция + валидация защищают от большинства конфликтов, но не от «последний победил».

### 14.3. Ограничения, связанные с Cotonti

- **Плагин работает только с `*_structure`** — не с `*_pages`, `*_market`, `*_forums`.
- **Не вызывает `*_sync()`** — `structure_count` не обновляется. Синхронизация — через `admin.php?m=structure&a=resyncall`.
- **Не управляет правами** — `*_auth` остаётся за штатным разделом Cotonti.
- **Не управляет шаблонами** — `structure_tpl` не меняется.

## 15. Диагностика и устранение неисправностей

### 15.1. Плагин не появляется в списке

**Симптом**: после загрузки файлов `admin.php?m=extensions` не показывает `dragstructure`.

**Причины:**

1. Файлы загружены не в `plugins/dragstructure/`, а в другое место.
2. `dragstructure.setup.php` не содержит блок `[BEGIN_COT_EXT]`.
3. Кеш Cotonti — очистить `datas/cache/`.

**Решение**: проверить путь, убедиться в наличии setup-файла, очистить кеш, обновить `admin.php?m=extensions`.

### 15.2. Страница открывается, но дерево пустое

**Симптом**: заголовок есть, `#category-tree` пуст, `NO_CATS` не показан.

**Причины:**

1. `CATS_JSON` сформирован некорректно (ошибка в `json_encode`).
2. JS упал на `buildByParent` из-за невалидных данных.
3. SortableJS не загрузился (CDN заблокирован).

**Диагностика**: открыть DevTools → Console → Network:

- Проверить загрузку `Sortable.min.js` (CDN).
- Проверить `let currentCats = {CATS_JSON};` в исходнике — валидный ли JSON.
- Проверить, что `document.getElementById('drag-structure')` не `null`.

### 15.3. Перетаскивание не срабатывает

**Симптом**: элементы видны, но не тянутся.

**Причины:**

1. SortableJS не инициализирован (JS упал до `initSortable`).
2. `.category-handle` — не тот класс, за который можно тянуть.
3. `handle: '.category-handle'` в конфиге SortableJS, но у элементов нет `.category-handle`.

**Диагностика**: проверить, что `initSortable(rootEl)` вызывается в `render()`, а в HTML есть `<i class="… category-handle"></i>`.

### 15.4. Перетаскивание срабатывает, но ответ ошибкой

**Симптом**: `alert()` с ошибкой, `location.reload()`.

**Возможные сообщения:**

| Сообщение | Причина |
|---|---|
| `Invalid CSRF token` | Сессия истекла, `xk` не совпадает |
| `Empty order` | JS передал пустой `order` |
| `Category #N not found` | Категория удалена параллельно |
| `Parent #N not found` | Родитель удалён параллельно |
| `Cannot move category into itself` | Перетаскивание в собственный контейнер |
| `Cannot move category into its own descendant` | Циклическое перемещение |
| `No categories in extension` | Область пуста |

**Диагностика**: DevTools → Network → `plug.php?r=dragstructure` → Response.

### 15.5. После перетаскивания публичная часть показывает старое

**Симптом**: в админке порядок обновлён, а в публичной части — старый.

**Причины:**

1. `Cot::$cache` не очищен (не должен случаться — `cache->clear()` в `move()`).
2. Отдельный кеш уровня nginx/Varnish.
3. Браузерный кеш — Ctrl+F5.

**Решение**: очистить серверный кеш (Varnish/nginx fastcgi_cache), проверить, что `Cot::$cache` включён и работает.

### 15.6. Нормализация «зависает»

**Симптом**: кнопка «Нормализовать» нажата, но UI не обновляется.

**Причины:**

1. Много категорий (1000+) — UPDATE'ы идут пачкой, время > 30 сек.
2. Timeout на стороне nginx/php-fpm.
3. Процесс убит OOM.

**Решение**: разбить нормализацию на пачки (ручная доработка) или увеличить `max_execution_time`/`memory_limit`.

### 15.7. Ошибки в логе PHP

**Симптом**: `admin.php?m=logger` содержит `PHP Warning: …`.

**Часто встречающиеся:**

- `Undefined index: dragstructure_saved` — не подключён `cot_langfile`.
- `Trying to access array offset on value of type null` — не переданы данные в шаблон.
- `Class Sortable not found` — JS-ошибка, не PHP.

**Решение**: проверить, что `require_once cot_langfile('dragstructure', 'plug')` выполняется до вызова `cot_rc()`. Проверить, что `$t->assign(…)` содержит все теги из шаблона.

## 16. Расширение и кастомизация

### 16.1. Кастомизация шаблона

**Способ 1: override в админ-теме**

Скопировать `plugins/dragstructure/tpl/dragstructure.tools.tpl` в `themes/<admin_theme>/plugins/dragstructure/dragstructure.tools.tpl` и редактировать. `cot_tplfile` найдёт его первым.

**Способ 2: правка исходника** — не рекомендуется (потеряется при обновлении).

### 16.2. Кастомизация через JS

Можно переопределить `render()`, добавив свой скрипт в `themes/<admin>/plugins/dragstructure/extra.js` и подключив его в шаблоне. Но `render` — локальная функция IIFE, доступ к ней снаружи закрыт.

**Альтернатива**: переопределить полностью `initSortable` через наследование или добавить кастомные поля в `buildNode` (например, иконку `structure_icon`).

### 16.3. Добавление своей области структуры

`dragstructure` **автоматически** подхватывает области из `cot_getExtensionsWithStructure()`. Чтобы добавить свою, модуль/плагин должен:

1. Объявить хук `structure.extensions` в `[BEGIN_COT_EXT]`.
2. В файле-плагине этого хука добавить `$extensionsWithStructure[] = 'my_ext';`.
3. Убедиться, что `structure_area='my_ext'` используется в таблице `*_structure`.

**Пример файла-плагина `myext.structure.extensions.php`:**

```php
<?php
defined('COT_CODE') or die('Wrong URL.');
$extensionsWithStructure[] = 'myext';
```

### 16.4. Добавление функциональности «создать категорию»

Сейчас плагин **не создаёт** категории. Если нужно — расширить `tools.php`:

1. Добавить форму создания (по аналогии с `admin.php?m=structure&a=add`).
2. Обработать POST через `cot_structure_add()`.
3. Добавить кнопку в `tools.tpl`.

Но проще — использовать штатный раздел Cotonti.

### 16.5. Добавление аудита

Для полного аудита логировать не только факт, но и детали:

```php
cot_log(
    "Structure. Drag&drop reorder in '$ext' (parent: $parentId). "
    . "Order: " . implode(',', $order),
    'adm',
    'structure',
    'update',
    ['extra_field' => json_encode($order)]
);
```

Требует настройки `*_logger` extrafields или просто расширения строки.

## 17. Производительность

### 17.1. Оценка сложности

| Операция | Сложность | Комментарий |
|---|---|---|
| `get_categories` | O(n) | Один SELECT |
| `validate_move` | O(n·m) | Циклы по `order` |
| `apply_order` (шаги 1–5) | O(n + m) | Сбор множеств |
| `apply_order` (шаг 6) | O(k) | k = потомки перемещаемых |
| `apply_order` (шаг 8) | O(k) UPDATE | k — изменённые |
| `move` (итого) | O(n + m + k·log k) | + транзакция |
| `normalize` | O(n) UPDATE | n — все категории области |

**n** — всего категорий в области, **m** — размер `order`, **k** — перемещаемое поддерево.

### 17.2. Реальные цифры

Для области `page` (~50 категорий) и типичного перетаскивания 1 категории:

- `get_categories`: ~1 мс
- `validate_move`: <1 мс
- `apply_order`: ~5–10 UPDATE, ~5–15 мс
- `cache->clear()`: 10–100 мс (зависит от драйвера)
- `cot_log`: ~1 мс
- **Итого**: ~20–120 мс

Для области `market` (~1000 категорий):

- `get_categories`: ~20–50 мс
- `apply_order`: 5–20 UPDATE (зависит от глубины)
- `cache->clear()`: 100–500 мс
- **Итого**: ~200–700 мс

### 17.3. Узкие места

1. **`cache->clear()`** — самая дорогая операция. На крупных сайтах — секунды.
2. **`get_categories` на больших областях** — вернуть все категории (для `CATS_JSON` и валидации).
3. **Рекурсивный `walkChildren`** — глубокие поддеревья (>100 потомков) дают O(k) с большим k.
4. **Двухфазное применение** — двойное число UPDATE.

### 17.4. Оптимизация (если станет проблемой)

1. **Не сбрасывать весь кеш**: заменить `Cache::clear()` на точечный `Cache::delete('structure')`. Требует анализа, какие ключи зависят от структуры.
2. **Пагинация `get_categories`**: если область >500 категорий, отдавать только верхние уровни, остальное — lazy load. Сейчас не реализовано.
3. **Батч-UPDATE** через `CASE WHEN` или `INSERT … ON DUPLICATE KEY UPDATE` (в MySQL) вместо `UPDATE` по одной. Ускорит в 3–5 раз.
4. **Отложенный `cache->clear()`** — через очередь. Сложнее в реализации.

### 17.5. Что уже оптимизировано

- **Двухфазное применение не выполняется**, если `dirty` пуст (быстрый выход).
- **`structure_path <> ?` в `normalize`** — не перезаписывает уже нормализованные пути.
- **`fetchAll` + `array_flip`** в `apply_order` — быстрый in-memory поиск.
- **`childrenMap`** — O(1) доступ к детям.

## 18. Сравнение со штатными инструментами Cotonti

### 18.1. Сравнительная таблица

| Возможность | `admin.php?m=structure` | `dragstructure` |
|---|---|---|
| Создание категорий | ✅ | ❌ |
| Удаление категорий | ✅ | ❌ |
| Редактирование title/desc/icon | ✅ | ❌ |
| Изменение `structure_path` вручную | ✅ (текстовое поле) | ❌ (автоматически) |
| Визуальный drag-and-drop | ❌ | ✅ |
| Автопересчёт путей | ❌ | ✅ |
| Рендер дерева | Плоский список с отступами | Полное дерево |
| Нормализация | ❌ | ✅ |
| Resync count | ✅ | ❌ |
| Управление шаблонами | ✅ | ❌ |
| Управление правами | Отдельный раздел | ❌ |

### 18.2. Когда что использовать

**Используйте `admin.php?m=structure`:**

- при создании/удалении категорий;
- при редактировании метаданных (title/desc/icon);
- для `resync count`;
- для управления шаблонами.

**Используйте `dragstructure`:**

- при массовой реорганизации иерархии;
- при необходимости визуального контроля порядка;
- для восстановления после сбоя.

### 18.3. Совместная работа

Плагин и штатный раздел **не конфликтуют**:

- оба читают/пишут `*_structure`;
- оба используют кеш (сбрасывают после изменений);
- оба следуют правилам `structure_path`.

**Рекомендуемый workflow**:

1. Создать категории через `admin.php?m=structure`.
2. Заполнить метаданные (title/desc/icon/tpl).
3. Организовать иерархию через `dragstructure`.
4. По необходимости — `resync count`.

| **`xk`** | CSRF-токен Cotonti (`Cot::$sys['xk']`). |
| **XSS** | Cross-Site Scripting — атака через инъекцию скриптов. Защита через `htmlspecialchars` и `JSON_HEX_*`. |
| **«Слипшиеся пути»** | Состояние, при котором `structure_path` содержит дубликаты или неконсистентные значения (например, `001` дважды). |
| **«Нормализация»** | Приведение всех путей области к плоскому списку `010`, `020`, … |
